# 주제 전환 구현 계획: 맛집 → 혜택·지원사업 카드뉴스 (핫수집 @hotsoozip)

## 0. 배경

맛집 카드뉴스는 **남의 사진에 의존하는 구조**라 자동화 범위가 계속 줄었다. Phase 3에서 "사진을 자동으로
가져오지 않는다"로 방향을 바꿨고(`_docs/insta-cardnews-automation-plan.md` Phase 3), 그 대안인 가게 공식 채널
찾기도 자동으로 찾는 비율이 약 25%에 그쳤다(`_docs/channel-finder-plan.md` §3). 결국 카드 1건마다 사람이
DM으로 허락을 받아야 해서 "워크플로우 자동화"라는 포트폴리오 목표와 맞지 않는다.

2026-10-06에 주제를 **청년정책·지원사업 등 "핫한 혜택 소식" 큐레이션**으로 바꾸기로 했다. 계정명은
`matsoozip`(맛수집) → **`hotsoozip`(핫수집)**. 핸들·로고 교체는 같은 날 끝냈고, 이 문서는 남은 **파이프라인
전환 작업**의 계획이다.

주제를 고른 기준:

- **사진이 필요 없다** — 텍스트와 템플릿만으로 카드가 완성된다
- **원천 데이터가 공공 API로 열려 있다** — 출처 표시 조건으로 재사용 가능한 데이터가 많다(데이터셋별 확인 필요, §3)
- **마감일이 있다** — "D-7 자동 발행" 같은 스케줄링에 이유가 생긴다
- **원문이 구조화 데이터다** — 금액·기간·자격을 LLM 결과와 대조해 자동 검증할 수 있다

## 1. 근거 정리 (우선순위 순)

1. **끝까지 자동화되는 파이프라인(주 근거)** — 수집 → 선별 → 카피 → 검증 → 렌더 → 발행 사이에 사람의 허락 단계가
   없다. 사람은 발행 전 검수만 한다.
2. **검증 가능한 LLM 활용(포트폴리오)** — "LLM이 사실을 지어내지 못하게 하는 구조"를 코드로 보여줄 수 있다.
   지금 `--handle`을 LLM 밖에서 주입하는 것과 같은 원칙을 금액·기간·자격으로 확장한다.
3. **피벗 서사(포트폴리오)** — 저작권 제약을 확인하고 데이터 소스를 재설계한 판단 과정 자체가 설명 가능한
   설계 결정이다. 그래서 맛집 시절 모듈과 문서는 지우지 않고 남긴다(§6).

## 2. 설계 원칙

- **사실은 LLM이 쓰지 않는다.** 정책명·지원 금액·신청 기간·대상·신청 링크는 API 원문에서 그대로 가져와
  코드가 주입한다. LLM은 후킹 문구와 한 줄 요약 같은 **카피만** 쓴다.
- **LLM 카피도 원문과 대조한다.** 카피에 나온 숫자(금액, 나이, 날짜)가 원문에 없으면 실패 처리한다.
- **모든 카드에 출처와 원문 링크를 남긴다.** 카드에는 출처 기관명, 게시물 캡션에는 원문 링크와
  "신청 전 공식 공고 확인" 안내를 넣는다.
- **공식 기관으로 보이지 않게 한다.** 프로필과 CTA 카드에 "비공식 큐레이션"임을 밝힌다.
- **마감이 지난 정보는 내보내지 않는다.** 선별 단계와 발행 직전에 마감일을 두 번 확인한다.
- **이미 올린 혜택은 다시 올리지 않는다.** 발행 이력을 저장해 중복을 걸러낸다.
- **사진은 쓰지 않는다.** 배경은 렌더러의 템플릿(카테고리별 색·패턴)으로 만든다.

## 3. 구현 전 조사 (Phase 0)

channel-finder 때처럼 **만들기 전에 실제 응답을 먼저 확인한다.** 아래 표의 소스·조건은 아직 확인하지 않은
후보이고, 조사 결과에 따라 이 문서를 수정한다.

| 후보 소스 | 내용 | 확인할 것 |
|---|---|---|
| 온통청년 청년정책 API | 청년정책 목록·상세 (1순위 후보) | 키 발급 절차와 소요 시간, 엔드포인트, 호출 한도, 이용 조건 |
| 공공데이터포털 "대한민국 공공서비스(혜택) 정보" (보조금24) | 전 연령 공공서비스 목록·지원조건 | 위와 같음 + 공공누리 유형 |
| 기업마당 지원사업 API | 소상공인·창업 지원사업 | 확장용. 1차 범위에서는 조사만 |

조사 스크립트(`apps/benefit-collector/src/test-*.js`)로 확인할 항목:

- **필수 필드가 채워지는 비율** — 정책명, 지원 내용, 신청 기간, 대상 조건, 신청 URL, 주관 기관
- **신청 기간 형식** — 날짜로 파싱되는 비율. "상시", "예산 소진 시까지" 같은 자유 텍스트가 얼마나 섞이는지
- **지원 내용 길이** — 카드 한 장에 들어갈 분량인지, LLM 요약이 필요한 수준인지
- **접수 중 + 마감 14일 이내** 조건으로 한 주에 몇 건이 나오는지 — 카드뉴스 1건(5~8장)을 채울 수 있는지
- **이용 조건** — 출처 표시 문구, 상업적 이용·변경 허용 여부

**완료 기준**: 소스 1개를 확정하고, 위 항목의 실제 수치를 이 문서 §3에 표로 적는다.

## 4. 데이터 흐름

```
[기존]  research-collector ──(txt)──▶ content-generator ──▶ image-matcher ──▶ card-renderer
         카카오 장소 + 네이버 트렌드      LLM 카피 전체 생성      허락받은 사진      PNG

[전환]  benefit-collector ──(json)──▶ content-generator ──▶ fact-check ──▶ card-renderer ──▶ publisher
         공공 API + 선별·중복 제거       LLM은 카피만,           숫자 대조        템플릿 배경      (Phase 4, 미구현)
                                        사실 필드는 주입
```

달라지는 점:

- **단계 간 전달이 텍스트에서 JSON으로 바뀐다.** 지금은 `*-adopted-*.txt`를 LLM에 통째로 넘겨서 구조가
  사라진다. 사실 필드를 주입하고 검증하려면 구조화된 채로 넘겨야 한다.
- **이미지 매칭 단계가 빠지고 검증 단계가 들어간다.**

## 5. 스키마 변경 (`shared/schemas/card-news.ts`)

장소 전용 필드를 혜택 필드로 바꾼다. 필드 이름을 재해석해서 쓰지 않고 새로 정의한다
(`place_name`에 정책명을 넣으면 3개월 뒤에 읽을 수 없다).

| 기존 (`CardNewsItem`) | 변경 | 채우는 주체 |
|---|---|---|
| `place_name` | `title` — 정책·사업명 | 코드 (API 원문) |
| `subtitle` | `subtitle` — 한 줄 요약 | LLM |
| `caption` | `caption` — 후킹 코멘트 | LLM |
| `address` | 삭제 | — |
| `image_keyword`, `image_url`, `image_credit` | 삭제 | — |
| — | `benefit` — 지원 내용 (예: "월 20만원, 최대 12개월") | 코드 (원문) 또는 LLM 요약 + 검증 |
| — | `target` — 대상 (예: "만 19~34세 무주택 청년") | 코드 (원문) 또는 LLM 요약 + 검증 |
| — | `period_end` — 신청 마감일 (`YYYY-MM-DD`, 상시는 `null`) | 코드 |
| — | `category` — 주거 / 일자리 / 금융 / 교육 / 복지 | 코드 |
| — | `source_name`, `source_url` — 주관 기관, 원문 링크 | 코드 |
| — | `source_id` — API의 정책 ID (중복 제거·검증용) | 코드 |

`CardNewsData`에는 `generated_at`(D-day 계산 기준일)과 `data_source`(출처 표시 문구)를 추가하고,
`cover_image_url`·`cover_image_credit`·`cta_card.image_url`·`cta_card.image_credit`은 삭제한다.

`benefit`·`target`은 원문이 길면 LLM 요약이 필요하다. 원문을 그대로 쓸지 요약할지는 Phase 0에서 본
필드 길이로 정한다.

## 6. 모듈별 작업

### 6.1 `apps/research-collector` → `apps/benefit-collector` (신규 작성)

- 공공 API 호출 → 정규화(§5 필드) → 선별 → 중복 제거 → `output/<timestamp>-adopted.json`
- **선별 규칙(초안)**: 접수 중 + 마감일이 오늘부터 3~14일 사이 → 마감 임박 순. 건수가 모자라면 범위를 넓힌다
- **중복 제거**: 발행 이력(`source_id`)에 있는 항목 제외. 이력은 Supabase 테이블 `published_benefits`에
  둔다(이미 `daily_insights`로 쓰고 있어 추가 인프라가 없다). publisher 구현 전에는 로컬 JSON 파일로 대체
- **시리즈 유형**: 1차는 "이번 주 마감 임박 혜택 N선" 하나만. 신규 공고·카테고리별 모음은 이후 확장
- 카카오 로컬·네이버 트렌드 코드는 새 수집기에서 쓰지 않는다. 기존 폴더는 §6.6 방침대로 남긴다

### 6.2 `apps/content-generator`

- `--input`을 JSON으로 받는다. LLM에는 항목별 원문을 넘기고, **응답 스키마에는 카피 필드만** 둔다
  (`hook_line`, `series_title`, 항목별 `subtitle`·`caption`, `cta_card`)
- 응답을 받은 뒤 `source_id`로 원문과 합쳐 사실 필드를 주입한다(지금 `source_handle` 주입과 같은 위치)
- `SYSTEM_PROMPT` 재작성: 장소 리서치 → 혜택 공고. "원문에 없는 금액·조건·기간을 쓰지 않는다" 규칙 추가
- `CARD_NEWS_RESPONSE_SCHEMA`(Gemini)와 `CARD_NEWS_ZOD_SCHEMA`(Claude) **두 벌을 같이** 수정
- `sample-input.txt` → 혜택 샘플 JSON으로 교체

### 6.3 검증 단계 (신규, `apps/content-generator/src/fact-check.js`)

- LLM이 쓴 필드에서 숫자 토큰(금액, 나이, 날짜, 개월 수)을 뽑아 해당 항목 원문에 있는지 대조
- 단위 정규화 필요: `20만원` ↔ `200,000원`, `만 19~34세` ↔ `19세 이상 34세 이하`
- 불일치 시 해당 항목을 1회 재생성하고, 다시 실패하면 파이프라인을 실패시킨다(틀린 정보를 내보내는 것보다 낫다)
- 마감일 재확인: `period_end`가 실행일보다 이전이면 실패
- 단위 테스트를 같이 작성한다(`node --test`, image-matcher의 테스트 방식과 동일)

### 6.4 `apps/card-renderer`

- **콘텐츠 카드 레이아웃 재설계** — 사진 위 오버레이 → 텍스트 중심 카드
  - 상단: 카테고리 칩 + D-day 배지 (`period_end`와 `generated_at`으로 계산)
  - 중앙: `title`(크게) → `benefit`(가장 강조) → `target`
  - 하단: 신청 마감일 + 출처 기관명
- **배경**: 사진 대신 카테고리별 색·패턴 템플릿. 브랜드 그라디언트(코랄–오렌지)를 기본으로 한다
- **커버 카드**: 배경 사진 제거, `series_title` + 건수 강조
- **CTA 카드**: 배경 사진 제거, "비공식 큐레이션 · 출처: <data_source>" 문구 추가
- `ImageCredit` 컴포넌트와 `/__images` 정적 경로 제거
- `sampleData.ts`, `shared/schemas/card-news.example.json`, `validate-card-news.js`를 새 스키마로 교체
- `design-reference/spec.md` 갱신 — 기존 레퍼런스(`places/*.png`)는 맛집 카드 기준이라 새 레퍼런스가 필요하다

### 6.5 `scripts/pipeline.js`

- 입력 탐색: `research-collector/output/*-adopted-*.txt` → `benefit-collector/output/*-adopted.json`
- 단계 구성: `1/3 카피 구조화` → `2/3 검증` → `3/3 렌더링` (이미지 매칭 단계 제거)
- 수집까지 한 번에 돌리는 `--collect` 옵션 추가(스케줄 실행용)

### 6.6 `apps/image-matcher` (보관)

- 파이프라인에서 떼어내되 **코드는 지우지 않는다.** README 맨 위에 "맛집 주제 시절 모듈, 2026-10-06 주제
  전환으로 미사용"을 적는다
- `robots.txt` 준수 크롤러(`polite-fetch.js`, `robots.js`)는 포트폴리오에서 따로 설명할 수 있는 결과물이다
- `images/_cta/matsoozip.jpg`(식당 사진)는 더 쓰지 않는다

### 6.7 `apps/insights-collector`, 대시보드

- 계정 ID와 토큰이 그대로면 코드 변경은 없다
- 주제 전환일(2026-10-06)을 대시보드에서 구분할 수 있게 기록한다 — 전환 전후 성과가 섞이면 비교가 안 된다

### 6.8 스케줄 실행 (`.github/workflows/benefits-weekly.yml`, 신규)

- 주 1회(초안: 월요일 KST 09:00) 수집 → 카피 → 검증 → 렌더 → PNG와 JSON을 아티팩트로 업로드
- 사람이 아티팩트를 확인하고 발행한다. publisher(Phase 4)가 생기면 승인 후 자동 발행으로 잇는다
- Secrets 추가: 공공 API 키, `GEMINI_API_KEY`, `ANTHROPIC_API_KEY`

### 6.9 문서·이름 정리

- 루트 `README.md`: 소개, 아키텍처 그림, 실행 예시를 새 주제로
- `_docs/insta-cardnews-automation-plan.md`: 맨 위에 주제 전환 안내와 이 문서 링크 추가(본문은 기록으로 유지)
- 각 앱 README의 맛집 예시 교체
- `apps/research-collector/data/topics.json`(강남 야장 등)은 새 수집기에서 쓰지 않는다

## 7. 단계와 완료 기준

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| Phase 0 | API 조사 (§3) | 소스 1개 확정, 필드 채움 비율·주간 건수를 문서에 기록 |
| Phase A | 스키마 + benefit-collector | `npm run collect`가 새 스키마의 사실 필드가 채워진 JSON을 낸다. 선별·중복 제거 단위 테스트 통과 |
| Phase B | content-generator + 검증 | 실제 API 데이터로 카피 생성, 일부러 틀린 숫자를 넣은 테스트에서 검증이 실패한다 |
| Phase C | card-renderer 재설계 | 실제 데이터 1건을 PNG로 렌더, 긴 정책명·긴 지원 내용에서 글자가 넘치지 않는다 |
| Phase D | pipeline + 스케줄 | `npm run pipeline -- --handle hotsoozip --collect` 한 번으로 PNG까지 나오고, GitHub Actions 수동 실행 성공 |
| Phase E | 문서 정리 | README와 계획서가 새 주제 기준, 저장소 검색에서 실행 경로에 "맛집"이 남지 않는다 |

Phase A~C는 스키마를 같이 쓰므로 **스키마를 먼저 확정**하고 들어간다.

|---|---|
| API 키 승인이 며칠 걸린다 | Phase 0에서 가장 먼저 신청. 기다리는 동안 샘플 JSON으로 Phase B·C 진행 |
| 신청 기간이 자유 텍스트라 마감일을 못 뽑는다 | 파싱되는 항목만 "마감 임박" 시리즈에 쓰고, 나머지는 제외. 비율은 Phase 0에서 확인 |
| LLM이 금액·자격을 틀리게 쓴다 | 사실 필드는 코드 주입, 카피는 숫자 대조(§6.3), 발행 전 사람 검수 |
| 게시 후 공고가 바뀌거나 조기 마감된다 | 캡션에 원문 링크와 확인 안내를 고정 문구로 넣는다 |
| 공식 기관 계정으로 오인된다 | 프로필·CTA 카드에 "비공식 큐레이션" 표기, 기관 로고는 쓰지 않는다 |
| 한 주에 조건에 맞는 공고가 모자란다 | 마감 범위를 넓히거나 "신규 공고" 시리즈로 대체. 최소 건수 미달이면 그 주는 발행하지 않는다 |
| 정규식 숫자 대조가 표현 차이를 못 잡는다 | 단위 정규화 규칙을 테스트로 쌓고, 못 잡는 유형은 검수 체크리스트에 올린다 |

## 9. 정해야 할 것

구현 전에 정하면 되는 항목이고, 괄호 안은 이 문서가 가정한 기본값이다.

- **대상 범위** — 청년정책만 할지, 전 연령 혜택까지 할지 (기본값: 청년정책으로 시작)
- **지역** — 전국 공고만 할지, 특정 지역 공고를 포함할지 (기본값: 전국 + 서울)
- **발행 주기** — (기본값: 주 1회, 월요일)
- **카드 장수** — (기본값: 커버 1 + 혜택 5 + CTA 1)
- **기존 게시물** — 맛집 시절 게시물이 있으면 보관 처리할지

## 10. 포트폴리오 서술 포인트

- **제약을 확인하고 방향을 바꾼 판단** — 사진 저작권 → 자동 수집 포기 → 채널 찾기 자동화율 25% → 주제 전환.
  각 단계에 조사 데이터와 문서가 남아 있다
- **LLM을 믿지 않는 구조** — 사실은 주입, 카피는 대조 검증, 실패하면 발행하지 않는다
- **조사 먼저, 설계는 그다음** — channel-finder와 같은 방식으로 Phase 0에서 실제 응답을 보고 계획을 고친다
- **재사용한 것과 버린 것** — 렌더러·LLM 폴백·인사이트 수집은 그대로, 수집기와 이미지 매칭만 교체
