# 가게 공식 채널 찾기(channel-finder) 구현 계획

## 0. 배경

Phase 3(실사 이미지)은 2026-09-28에 **"사진을 자동으로 가져오지 않는다"**로 방향을 바꿨다
(`_docs/insta-cardnews-automation-plan.md` Phase 3 "원안 폐기" 참고). 카카오맵/네이버 지도/Google Places의
사진은 공식 사진이어도 제3자 계정에 재게시할 권리가 없고(사진 탭에는 방문자 리뷰·블로그 사진도 섞여 있어
사장님조차 권리가 없는 경우가 있음), 카카오맵은 `robots.txt`로 장소 페이지 수집 자체를 막고 있기 때문이다.
2026-09-30에 "네이버 지도 업체 사진을 쓰면 안 되나"를 다시 검토했고, 같은 이유로 현재 방향을 유지하기로 했다.

그래서 Phase 3는 세 단계가 됐다:

1. **가게 공식 채널 찾기 (자동 + 수동 보조)** ← 이 문서
2. 사용 허락 요청 (사람, DM)
3. 허락받은 사진 → 카드 반영 (자동, `apps/image-matcher/src/match.js` — 구현 완료)

## 1. 근거 정리 (우선순위 순)

1. **허락 요청 작업량 감소(주 근거)** — 카드뉴스 1건당 장소 8곳 × 수동 검색. 찾을 수 있는 건 자동으로 찾고,
   못 찾은 건 사람이 클릭 몇 번으로 확인할 수 있게 정리한다.
2. **크롤링 학습(학습 목적)** — `robots.txt` 해석, User-Agent 명시, 요청 간격 제한, HTML 파싱, 실패 처리를
   직접 구현해본다. 단 **허용된 곳만** 대상으로 한다.
3. **파이프라인 서사(포트폴리오)** — "약관·저작권을 지키면서 자동화할 수 있는 부분만 자동화한다"는 판단 과정,
   그리고 조사 데이터로 설계를 수정한 과정 자체가 설명 가능한 설계 결정이 된다.

## 2. 설계 원칙

- **사진은 절대 가져오지 않는다.** 이 모듈의 출력은 "연락할 곳(URL/계정) 후보"뿐이다.
- **플랫폼 페이지를 직접 긁지 않는다.** 카카오맵·네이버·인스타그램 도메인에는 요청하지 않는다 — 문서 약속이 아니라
  `polite-fetch.js`의 **차단 도메인 목록으로 코드에서 강제**한다. 인스타 계정은 검색 API 결과나 가게 홈페이지에
  이미 적힌 링크에서만 얻는다.
- **크롤링은 가게 자체 홈페이지에만, `robots.txt`가 허용할 때만** 한다. 확인 불가(타임아웃/5xx)도 "불허"로 취급한다.
- **근거 없는 후보를 만들지 않는다.** 웹문서·블로그에서 뽑은 계정은 조사 결과 대부분 후기 작성자였으므로(§3) 단독
  후보로 내지 않고, 다른 소스의 후보를 **뒷받침할 때만** 근거로 붙인다.
- **자동으로 확정하지 않는다.** 결과는 근거가 붙은 **후보**이고, 맞는 계정인지는 사람이 판단한다.
- **파이프라인 필수 단계가 아니다.** 허락 요청은 사람이 하는 일이라 `npm run pipeline`에 넣지 않고 별도 명령으로 둔다.

## 4. 데이터 소스와 역할

모두 NAVER API HUB Search API (인증: `X-NCP-APIGW-API-KEY-ID` / `X-NCP-APIGW-API-KEY`). 현재 한시적 무료,
검색 API 월 775,000건·키당 50 RPS (2026-09-30 NCP 가이드 확인). 1회 실행 = 장소 8곳 × 3건 = 24건.

| 소스 | 엔드포인트 | 역할 |
|---|---|---|
| 지역 검색 | `GET https://naverapihub.apigw.ntruss.com/search/v1/local` | **주 소스.** `roadAddress`로 같은 가게인지 검증 후 `link` 분류: 인스타 → 후보, 자체 도메인 → 홈페이지 후보, 플랫폼 도메인 → 무시 |
| 가게 홈페이지 (크롤링) | 지역검색에서 얻은 자체 도메인 | **주 소스.** `robots.txt` 허용 시 메인 페이지 1장에서 `<a href>`의 인스타 링크 추출 |
| 웹 문서 검색 | `GET .../search/v1/webkr` | **보조 근거만.** 이미 있는 후보 계정이 나오면 근거로 추가. 새 후보는 만들지 않음 |
| 블로그 검색 | `GET .../search/v1/blog` | **보조 근거만.** 웹문서와 동일 |

## 5. 아키텍처

```
apps/image-matcher/
├── src/match.js              # (기존) 허락받은 사진 → 카드 반영
├── src/find-channels.js      # 신규 CLI: npm run find-channels -- --data <카드 JSON>
├── src/lib/
│   ├── naver-search.js       # local / webkr / blog 호출
│   ├── extract.js            # 태그 제거, 주소 정규화, 인스타 계정 추출, URL 분류(인스타/플랫폼/홈페이지)
│   ├── robots.js             # robots.txt 파서 (RFC 9309, 학습 목적으로 직접 구현)
│   └── polite-fetch.js       # 차단 도메인 강제, UA 명시, 호스트당 간격, 타임아웃, 크기 제한, 리다이렉트 수동 처리
└── test/                     # node:test — extract, robots 단위 테스트
```

**처리 흐름 (장소 1곳 기준)**

```
카드 JSON의 cards[] (place_name, address)
  1. 지역검색 "<장소명> <구>" → roadAddress 정규화 값이 카드 주소와 같은 항목 선택
     └ link 분류: instagram.com/<계정> → 인스타 후보 / 자체 도메인 → 홈페이지 후보 / 플랫폼 → 무시
  2. 홈페이지 후보가 있으면: robots.txt 확인 → 허용 시 메인 1장 → <a href>의 인스타 링크 → 인스타 후보
     └ 불허·실패는 skipped에 이유와 함께 기록 (홈페이지 자체는 연락 채널 후보로 남김)
  3. 웹문서·블로그 "\"<장소명>\" <구> 인스타그램" → 장소명이 든 결과에서 계정 추출
     └ 이미 있는 인스타 후보와 같으면 근거 추가, 아니면 버림
  4. 후보가 없으면: 사람용 수동 확인 링크(네이버 지도 검색, 네이버 검색)만 출력
```

**신뢰도**

- 높음: 지역검색 `link`가 인스타 / 홈페이지에 적힌 인스타 / 두 개 이상 소스 일치
- 중간: 홈페이지 자체 (연락 채널로는 유효하지만 인스타는 아님)

**추출 규칙 (extract.js)**

- `instagram.com/<계정>`만 계정으로 인정. `p/`, `reel/`, `reels/`, `explore/`, `stories/`, `accounts/`, `tv/`, `direct/` 제외
- 계정명 정규화: 소문자, 쿼리스트링·끝 슬래시·끝 마침표 제거, 인스타 계정 규칙(영문/숫자/`.`/`_`, 30자 이하)
- 텍스트의 `@계정`은 앞이 공백/문장 시작/괄호일 때만 (이메일 오탐 방지)
- 검색 결과의 `<b>` 태그·HTML 엔티티 제거 후 처리
- 플랫폼 도메인: `naver.com`, `naver.me`, `kakao.com`, `daum.net`, `instagram.com`(계정 링크는 인스타 후보로 따로 처리),
  `facebook.com`, `youtube.com`, 맛집 집계 사이트(`siksinhot.com`, `polle.com`, `visitseoul.net`, `diningcode.com`, `mangoplate.com`) 등 → 홈페이지 후보에서 제외

**크롤링 에티켓 (polite-fetch.js / robots.js)**

- 차단 도메인(네이버·카카오·다음·인스타그램·페이스북 계열)은 요청 자체를 거부 — 코드로 강제
- User-Agent: `cardnews-channel-finder/0.1 (+https://github.com/7saval/cardnews)` — 누가 왜 요청하는지 밝힘
- `robots.txt`: 우리 UA 그룹 → 없으면 `*` 그룹, Allow/Disallow는 가장 긴 매칭 우선(동률이면 Allow), `*`/`$` 패턴 지원.
  호스트별 캐시(1회 실행 동안). 4xx면 전부 허용, 5xx/네트워크 오류면 전부 불허
- 같은 호스트에 1초 이상 간격, 요청 타임아웃 10초, 응답 2MB 초과 시 중단, `text/html`만 파싱
- 리다이렉트는 자동으로 따라가지 않고 최대 3회까지 **다음 주소마다 차단 도메인·`robots.txt`를 다시 확인**
- 홈페이지당 메인 페이지 1장만 (링크를 따라 내려가지 않음)
- 실제로 보낸 요청 URL을 전부 출력 JSON(`requests`)에 기록 — 플랫폼 도메인에 요청하지 않았음을 확인 가능

## 8. 완료 기준

- `npm run find-channels -- --data <카드 JSON>` 한 번으로 **모든 장소가 체크리스트에 오른다** — 찾은 곳은 근거와 함께,
  못 찾은 곳은 수동 확인 링크와 함께
- 근거가 웹문서·블로그뿐인 계정은 후보로 나오지 않는다 (§3 오탐 방지)
- 네이버·카카오·인스타그램 도메인에는 요청을 한 번도 보내지 않는다 (`requests` 로그로 확인)
- `robots.txt`가 막은 홈페이지는 건너뛰고, 건너뛴 이유가 출력에 남는다

## 9. 열린 질문

- **체인점 처리** — "영동소금구이 논현본점"처럼 지점명이 붙은 경우 본점 계정과 지점 계정이 다를 수 있다.
  우선은 후보를 모두 보여주고 사람이 고르게 한다.
- **`robots.txt` 파서 직접 구현 vs 라이브러리** — 학습 목적으로 직접 구현하되, 단위 테스트로 표준 동작(RFC 9309)과
  맞는지 검증한다. 테스트가 과하게 복잡해지면 `robots-parser` 패키지로 교체 검토.
- **자동 탐지율 개선** — 25%는 한 주제(강남 야장) 기준. 다른 주제로도 쌓아보고, 낮게 유지되면 카카오 로컬 API 응답의
  필드 중 활용 가능한 게 있는지 추가 검토.
