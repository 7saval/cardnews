### 5. 두 번째 실행 — 504로 즉시 실패 → 시간 초과는 재시도 없이 바로 Haiku

```
  관련성 점수: 캐시 0건, 새로 매길 것 117건
✘ 수집 실패: {"error":{"code":504,"message":"Deadline expired before operation could complete.","status":"DEADLINE_EXCEEDED"}}
```

- 원인 분석은 아래 문제 3. 작업 4의 타임아웃이 서버 deadline으로도 쓰여서 서버가 먼저 504로 끊었고, 504는 폴백 대상이 아니었음
- 로컬 실측: 30건 묶음 한 번에 **381초** (입력 8,985 / 출력 2,728 토큰). 평소라면 수십 초일 양 — Gemini가 심하게 느린 상태
- 규칙 재정리 (두 앱 공통):

| 실패 종류 | 판정 | 처리 |
|---|---|---|
| 429·500·503 | 일시적 오류 | 같은 Gemini로 지수 백오프 재시도(최대 4회) → 그래도 실패면 Haiku |
| 504·클라이언트 abort | 시간 초과 (`isDeadlineError`) | **재시도 없이** 바로 Haiku — 느린 서버에 다시 보내면 또 120초 |
| 400·401·403 등 | 우리 쪽 문제 | 폴백 없이 실패 |

- 작업 4에서 넣은 "타임아웃도 재시도"는 되돌림 (`isRetryableError` → `isDeadlineError` + `shouldFallBackFromGemini`)
- `GEMINI_TIMEOUT_MS`는 최소 10초로 고정 — 서버가 10초 미만 deadline을 400으로 거절함
- 테스트 수정: 504·abort는 폴백·재시도 안 함, 400·401은 폴백 안 함, SDK가 `x-server-timeout` 헤더를 보내는지
- **실제 API로 폴백 확인** (`GEMINI_TIMEOUT_MS=10000`, 5건씩 2회): 1회차 Gemini 10초 무응답 → Haiku 16.3초, 2회차 바로 Haiku 6.8초, 둘 다 점수 5/5. Anthropic 키·`claude-haiku-4-5` 정상
- 테스트: 두 앱 모두 27개 통과

## 🐛 발생한 문제 & 해결

### 문제 1: Actions 실행이 503 재시도 2회 후 아무 출력 없이 멈춤

- **원인**:
  - 세 번째 요청이 503으로 실패했다면 `(3/3)` 줄이 찍혀야 함 → 실패도 성공도 아닌 **응답 대기 중**
  - `@google/genai` 2.30.0은 Node fetch(undici)의 기본 300초 header/body 타임아웃을 **일부러 0으로 꺼 둠**. 주석: "no client-side timeout by default (the server bounds requests: 10 min unary)". `httpOptions.timeout`을 주지 않으면 요청 하나가 최대 10분 매달림
  - 끝내 끊겨도 에러에 `status`가 없어서 기존 코드는 Haiku로 넘어가지 않고 그대로 실패했을 것
- **해결**: 위 작업 4. 수정 전 실행은 Actions에서 취소
- **참고**: `node_modules/@google/genai/dist/node/index.mjs`의 `createUndiciNoTimeoutDispatcher`, `createAttemptSignal` (타임아웃은 재시도마다 새로 걸림)

### 문제 2: 파이썬 치환 스크립트가 `\n` 이스케이프에서 불일치

- **원인**: bash heredoc 안의 파이썬 문자열에 JS 소스의 `` `\n⚠ `` 를 `\\n`으로 넣었는데 매칭 실패
- **해결**: `assert` 덕분에 파일에 쓰기 전에 멈춤. 이스케이프가 없는 부분 문자열로 나눠 다시 치환
- **참고**: 치환마다 `count == 1` 검사를 넣어 두니 부분 적용 없이 안전하게 실패했다. 10-21 문제 1과 같은 계열 — 이스케이프가 섞인 문자열은 피해서 치환한다

### 문제 3: 타임아웃을 넣었더니 `504 DEADLINE_EXCEEDED`로 즉시 실패

- **원인**:
  - SDK는 `httpOptions.timeout`을 `X-Server-Timeout` 헤더(초 단위)로 **서버에도 보낸다** (`getHeadersInternal`). 그래서 클라이언트 abort보다 서버가 먼저 120초에 끊고 504를 돌려줌
  - 작업 4의 테스트는 가짜 로컬 서버라 헤더를 무시했고, 클라이언트 abort(`AbortError`)만 확인함 → 실제 Gemini의 504 경로를 못 잡음
  - 504가 `GEMINI_RETRYABLE_STATUS`에 없어서 폴백 없이 실패
- **해결**: 작업 5. 테스트에 헤더 확인을 추가하고, 실제 API로 폴백 경로를 한 번 돌려 확인
- **참고**: 실측 중 `GEMINI_TIMEOUT_MS=3000`은 `400 "Manually set deadline 3s is too short. Minimum allowed deadline is 10s."` → 하한 10초 추가

## 💡 배운 점 / 메모

- **"재시도·폴백 있음"이 곧 "멈추지 않음"은 아니다.** 실패는 ① 에러 응답 ② 응답 없음 두 가지이고, ②는 타임아웃이 있어야 ①로 바뀐다. 외부 API 호출에는 항상 상한을 둔다
- SDK마다 기본 타임아웃이 다르다. Gemini JS SDK는 기본 없음(+ Node 기본값도 끔), Anthropic SDK는 기본 10분 + 자체 재시도 2회. 기본값을 믿지 말고 확인한다
- 로그로 "어디서 멈췄는지" 추론하기: 다음에 나와야 할 줄이 안 나왔으면 그 사이의 호출이 끝나지 않은 것
- 실제 SDK + 응답 없는 로컬 서버(`http.createServer(() => {})`)로 타임아웃 에러 모양을 테스트할 수 있다. 에러 이름을 추측하지 않고 확인 (`AbortError`, `status` 없음)
- CI는 로컬 캐시가 없으니 **첫 실행이 가장 무겁다** (점수 117건 전부 LLM 호출). 두 번째부터는 `actions/cache`로 복원됨
  - 단, 실패한 실행은 캐시가 저장되지 않아(`actions/cache`는 job 성공 시 저장) 성공할 때까지 매번 117건을 다시 매긴다
- **가짜 서버 테스트는 실제 서버의 동작을 다 흉내내지 못한다.** 클라이언트 쪽 타임아웃 분류는 확인됐지만, 서버가 헤더를 보고 먼저 504를 낸다는 건 실제 API에서야 드러났다. 폴백 같은 비상 경로는 실제 API로 한 번은 강제로 태워 본다
- 실패를 "재시도할 것"과 "바로 다른 길로 갈 것"으로 나눈다. 과부하 거절(503)은 잠깐 뒤 풀릴 수 있지만, 시간 초과는 느린 상태 그 자체라 재시도가 비용만 키운다
