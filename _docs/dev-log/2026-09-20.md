## ✅ 완료한 작업

### 1. 프로젝트 폴더 구조 생성

계획서(`_docs/insta-cardnews-automation-plan.md`) 5번 섹션대로 `apps/`, `design-reference/`, `shared/schemas/`, `.github/workflows/`를 미리 만들어둠. `_docs/`는 기존 문서 폴더라 건드리지 않음.

### 2. 레퍼런스 디자인 분석 → `design-reference/spec.md`

- `design-reference/places/`에 넣어준 실제 카드뉴스 스크린샷(`timesquare_1~5.png`, `cta_1.png`, `cta_2.png`)을 열어서 레이아웃을 픽셀 단위로 분해
- 커버 카드(두꺼운 아웃라인 타이포 4줄), 콘텐츠 카드(하단 그라데이션 오버레이 + 상호명/주소/캡션), CTA 카드(인스타 프로필 카드를 그대로 미러링) 세 가지 스펙을 CSS 초안까지 포함해서 정리
- CTA 레퍼런스 2종(`nyam` 앱 광고 스타일 vs `서울픽` 프로필 카드 스타일) 중, 계획서 의도(팔로우 유도)에 맞는 후자를 채택 근거와 함께 문서화

### 3. `apps/card-renderer` — React + Vite 카드 렌더러

- `CoverCard.tsx` / `ContentCard.tsx` / `FollowCTACard.tsx` 3종 컴포넌트 제작, `spec.md` 기준으로 스타일링
- Black Han Sans(아웃라인 타이포용) + Noto Sans KR(본문) Google Fonts 연결
- 참고 파일: `apps/card-renderer/src/components/`

### 4. 화살표·캐러셀 dot 디자인 요소 제거

사용자가 "인스타 캐러셀은 화살표/dot을 앱이 자동으로 그려주는데, 카드 이미지 안에도 그리면 중복 아니냐"고 지적 → 실제로 레퍼런스 스크린샷의 화살표/dot은 인스타그램 UI 크롬이 찍힌 것이지 업로드 이미지 자체의 디자인 요소가 아니었음을 확인. `CoverCard`/`ContentCard`/`FollowCTACard`, `cards.css`, `spec.md`에서 관련 코드·설명을 전부 제거.

### 5. Playwright 렌더링 스크립트 + JSON 스키마 확정 (Plan Mode)

- `shared/schemas/card-news.ts`로 카드뉴스 타입 정의를 앱 밖으로 꺼내서 공유 가능하게 만듦 (계획서 원안 대비 추가된 필드는 파일 상단 주석으로 명시)
- `shared/schemas/card-news.example.json` — 계획서 원본 예시를 실제 파일로 저장
- `apps/card-renderer/src/App.tsx`에 `window.__RENDER_DATA__` 폴백 로직 추가 — Playwright가 `page.addInitScript()`로 임의 데이터를 주입하면 그걸 쓰고, 없으면 내장 샘플로 폴백 (fetch/useEffect 없이 동기 처리)
- `apps/card-renderer/scripts/render.js` — `npm run render -- --data <JSON> --out <폴더>` 한 줄로 JSON을 카드별 PNG(`01-cover.png`, `02-<장소명>.png`, ...)로 렌더링하는 CLI. 입력 JSON 검증 로직 포함(필수 필드 누락 시 구체적 에러)

### 6. `apps/content-generator` — Gemini API로 카피 구조화

- `@google/genai` SDK로 리서치 원본 텍스트(`sample-input.txt`, 을지로 노가리 골목 3곳을 흉내낸 테스트 데이터)를 넣으면 `card-news.ts` 스키마에 맞는 JSON을 뽑아내는 `src/generate.js` CLI 제작
- `src/prompt.js`에 시스템 프롬프트 + Gemini `responseSchema`(OpenAPI 스타일) 정의. `source_handle`/`cta_card.handle`은 LLM이 지어내면 안 되는 "계정 정보"라 스키마에서 제외하고 `--handle` CLI 인자로 생성 후 주입
- 검증 로직(`assertValidCardNewsData`)을 `apps/card-renderer/scripts/render.js`에서 `shared/schemas/validate-card-news.js`로 옮겨서 두 앱이 공유하도록 리팩터링
- 실제 Gemini API 호출로 을지로 호프집 3곳짜리 카드뉴스 JSON 생성 → `card-renderer`로 렌더링까지 성공 (리서치 텍스트 → LLM → JSON → PNG 전체 1회 완주)

### 7. 계획서 문서 정비

- 완료된 체크리스트 항목 5개 체크 (레퍼런스 스펙/JSON 스키마/React 컴포넌트/Playwright 스크립트/LLM 프롬프트)
- 각 앱을 자동으로 잇는 오케스트레이션이 아직 없다는 점을 1번 섹션 주석 + 6번 체크리스트에 명시
- `## 9. 로컬 실행 및 확인 명령어` 섹션 신규 추가 — `npm run dev`/`npm run render`/`npm run generate` 사용법과 결과물 위치 정리

### 8. 계획서 소재 리서치·이미지 매칭 전략 수정 (상세)

Phase 1 구현을 진행하면서 원래 계획서(1주차 초안)의 두 부분이 실제 소재 특성과 안 맞는다는 문제의식이 생겨서 계획서 자체를 수정함.

**① 소재 리서치 — 트렌드 데이터를 "선택사항"에서 "핵심 조합 요소"로 격상**

- **기존 문제**: 계획서 원안에서는 카카오 로컬/네이버 지역검색 API로 장소를 검색하는 게 메인이고, 트렌드 데이터(pytrends/네이버 데이터랩)는 "선택"으로 분류되어 있었음. 하지만 이 API들은 키워드+지역으로 검색되는 장소를 "다 보여줄 뿐" 그중 어떤 장소를 카드뉴스로 다룰지 우선순위를 판단해주지 않음.
- **변경**: 카카오/네이버 API가 만든 장소 후보 리스트에 트렌드 데이터(검색량·상승세)로 스코어링을 걸어서, "지금 화제성 있는 장소"만 자동으로 걸러내는 필터/랭킹 로직으로 역할을 재정의. 즉 API는 "장소 데이터"를, 트렌드 데이터는 "이 장소를 지금 다룰 가치가 있는가"를 판단하는 두 축의 조합으로 소재 리서치 단계를 다시 설계함.
- **이유**: 이렇게 해야 시리즈 주제(예: "요즘 뜨는 야장")까지 자동으로 도출할 수 있어서, 사람이 매번 "이번엔 뭘 다룰지" 정해줘야 하는 병목이 줄어듦.

**② 이미지 매칭 — Unsplash/Pexels(범용 스톡)에서 실사 장소 이미지 자동 매칭으로 전환**

- **기존 문제**: 계획서 원안 Phase 3은 Unsplash/Pexels API로 `image_keyword`(예: `"seoul rooftop bar sunset"`) 기반 검색을 해서 배경 이미지를 매칭하는 방식이었음. 그런데 소재가 실존하는 특정 장소("가가바" 같은 실제 술집)인 이상, 범용 키워드로 검색한 스톡 사진은 그 장소와 전혀 무관한 "아무 바 사진"이 나올 수 있음 — 실사 장소를 다루는 콘텐츠에서 이건 신뢰도 문제로 직결됨.
- **변경**: 장소가 실제로 등록한 사진을 우선 쓰는 전략으로 교체.
  1. 카카오 로컬 API의 `place_url`, 네이버 지역검색 API의 `link`로 연결되는 상세페이지(카카오맵/네이버플레이스)에서 대표 이미지를 크롤링 (1순위, 무료, 매칭 정확도 최고)
  2. Google Places API Photos — 크롤링 리스크를 피하고 싶을 때의 공식 API 대안 (유료지만 월 $200 무료 크레딧으로 충분히 커버, 라이선스 처리가 구글 쪽에서 이뤄짐)
  3. 소재 리서치 때 이미 수집 중인 블로그 포스트의 `og:image`를 폴백으로 재활용 (추가 비용 없음)
  4. 초기엔 휴먼인더루프 검수 → 매칭 정확도가 검증되면 자동 채택으로 전환
- **Unsplash/Pexels를 완전히 버리진 않음**: 지금은 소재가 "실존 장소"로 한정돼 있어서 안 맞지만, 나중에 카드뉴스 주제를 실물 장소가 없는 영역(라이프스타일 팁, 감성 카피 등)으로 확장하면 다시 필요해짐. 그래서 삭제하지 않고 계획서 맨 아래 `## 8. 향후 확장 아이디어` 섹션으로 옮겨서 "주제 확장 시 도입" 항목으로 남겨둠.
- 이 변경에 맞춰 계획서의 기술스택 표, 비용 표, 폴더 구조 설명, 체크리스트도 함께 갱신함.
- 참고 파일: `_docs/insta-cardnews-automation-plan.md` (1, 3, 5, 6, 8번 섹션)

## 🐛 발생한 문제 & 해결

### 문제 1: 카드 디자인에 화살표/캐러셀 dot이 중복으로 들어감
- **원인**: 레퍼런스 스크린샷을 분석할 때 인스타그램 앱/웹의 UI 크롬(화면 캡처 시 같이 찍힌 것)을 실제 카드 디자인 요소로 착각함
- **해결**: 사용자 지적으로 발견 → 컴포넌트/CSS/spec.md에서 전부 제거하고, 왜 뺐는지 spec.md에 근거를 남겨둠
- **참고**: `design-reference/spec.md` 0번 섹션 하단 "[수정]" 메모

### 문제 2: `@google/genai` 호출 시 `TypeError: unusable` 에러
- **원인**: SDK 기본 재시도 옵션(최대 5회)이 실패한 요청을 재시도할 때, 이미 소모된 요청 본문 스트림을 재사용하려다 발생하는 버그로 추정
- **해결**: 에러 핸들러에 `err.cause`/`err.stack` 로깅을 추가해 원인을 좁힌 뒤, `new GoogleGenAI({ httpOptions: { retryOptions: { attempts: 1 } } })`로 재시도를 꺼서 우회. 이후 정상 호출 성공
- **참고**: `apps/content-generator/src/generate.js`

### 문제 3: Gemini Node SDK의 API 형태가 예상과 다름
- **원인**: 기존에 알고 있던 `ai.models.generateContent()` 방식이 아니라 `ai.interactions.create()` 방식으로 API 표면이 바뀌어 있었음 (SDK 메이저 버전 2.x)
- **해결**: 공식 문서(ai.google.dev)를 직접 조회해서 최신 사용법(`input`, `system_instruction`, `response_format.{type, mime_type, schema}`, `interaction.output_text`)을 확인하고 그대로 구현. 임의 추측으로 구현하지 않고 라이브 문서 확인을 거침

## 💡 배운 점 / 메모

- 캐러셀 게시물 스크린샷을 레퍼런스로 쓸 때는 "실제 업로드된 이미지"와 "보는 앱이 얹어주는 UI"를 구분해서 봐야 한다 — 안 그러면 중복 렌더링하게 됨
- Playwright로 특정 데이터를 렌더링해서 캡처하고 싶을 때, fetch+로딩 상태 없이 `page.addInitScript()`로 `window.전역변수`를 미리 심어두는 패턴이 훨씬 단순함 (동기적으로 값을 읽을 수 있어서 React 컴포넌트가 복잡해지지 않음)
- TypeScript에서 `import type`(타입 전용 임포트)은 런타임에 실제로 파일을 읽지 않기 때문에, 번들러(Vite)의 파일시스템 접근 제한(`server.fs.allow`)에 걸리지 않는다 — 별도 모노레포 툴링 없이도 `shared/` 폴더의 타입을 앱들이 자유롭게 공유할 수 있는 이유
- 외부 라이브러리(특히 최근에 API 형태가 바뀐 SDK)를 쓸 때는 기억에 의존하지 말고 최신 공식 문서를 직접 확인하는 게 안전함 — `@google/genai`가 실제로 메이저 버전이 올라가면서 API 표면이 바뀌어 있었음
- 에러 메시지가 짧고 불친절할 때(`TypeError: unusable`)는 `error.cause`/`error.stack`을 먼저 찍어보는 게 원인 추적의 첫 단추
- 소재의 성격(실존하는 특정 장소 vs 범용 콘텐츠)에 따라 이미지 소스 전략이 완전히 달라져야 한다 — 구현 전에 계획서에서 먼저 잡아뒀기 때문에, 렌더러/스키마를 다 만든 뒤에 갈아엎는 대신 이미지 매칭(Phase 3) 착수 전에 미리 방향을 바로잡을 수 있었음
