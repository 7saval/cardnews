## ✅ 완료한 작업

### 1. 11-16 주간 실행 실패 추적

#### 배경·문제 정의
- 11-14에 첫 회차를 게시하고 `published.json`을 채웠으니, 11-16 주간 실행에서는 카테고리가 생활안정에서 넘어가야 했다. 그 확인을 하려고 실행 기록을 열었는데 `benefits-weekly`가 **실패**해 있었다.
- 실패 알림이 없어서 6일 동안 몰랐다. 11-14 데브로그에 "인사이트 수집 실패를 7주 동안 몰랐다 → 알림 필요"라고 적어 두었는데, 같은 일이 한 번 더 생겼다.

#### 조사·원인 추적
- `gh run list`로 11-14 이후 실행을 확인했다. `insights-daily`는 11-14부터 매일 성공했고, `benefits-weekly`(11-16)만 3분 8초 만에 실패했다.
- `gh run view --log-failed`로 실패한 단계의 로그를 봤다.
  - 카테고리 순환은 **정상**이었다. 생활안정 다음으로 `고용·창업: 후보 41건`이 선택됐다.
  - 관련성 점수를 Gemini로 시도했지만 120초 안에 응답이 없었다. 그래서 Haiku로 넘어갔는데, Haiku 호출이 `401 authentication_error: invalid x-api-key`로 실패했다.
- 11-14에 로컬 `.env`의 Anthropic 키가 무효여서 교체했을 때는 GitHub Secret의 키가 정상이었다. 그 사이에 Secret 키가 무효가 된 것이다.
- 연쇄 영향: 수집 단계에서 실패하는 바람에 `relevance-cache.json`이 만들어지지 않았다. 그래서 artifact 업로드도 `No files were found`로 건너뛰었다. 11-23에 하려던 "캐시 복원 확인"이 한 주 밀린다.

#### 원인
- **확정**: GitHub Secret `ANTHROPIC_API_KEY`가 무효였다(401).
- **추정**: 11-14 데브로그의 "노출된 예전 키 삭제" 후속 작업을 하다가 Secret이 쓰던 키까지 지웠을 가능성이 있다. Console의 키 목록과 대조하지는 않았다.

#### 해결·결과
- Console에서 용도별 이름을 붙인 새 키(`cardnews-github-actions`)를 발급하고 Secret을 갱신했다(09:45 UTC). 키를 대화나 셸 기록에 남기지 않도록 웹 UI로 넣었다.
- 수동 실행(run 45009185288)이 **8분 11초 만에 성공**했다.
  - 고용·창업 후보 41건 → Haiku로 점수 41/41 → 5건 선정
  - 카피를 생성하고 fact-check를 거쳤다. 1회차에서 `details: 원문에 없는 숫자 "491개"`가 걸렸고, 재생성한 2회차가 통과했다.
  - artifact `cardnews-6`(카드 PNG 7장 + 캡션)과 `relevance-cache`가 올라갔다.

#### 배운 점
- 키 이름이 용도를 드러내지 않으면, 정리하다가 엉뚱한 키를 지우게 된다. 그래서 키 이름에 "어디서 쓰는지"를 넣었다.
- 실패 알림은 이제 "있으면 좋은 것"이 아니라 우선순위 1순위다. 두 번 연속으로 사람이 우연히 들여다보다가 발견했다.

### 2. 기본 LLM 프로바이더를 Gemini → Claude Haiku로 교체

#### 배경·문제 정의
- 1번을 추적하면서 패턴이 보였다. **Gemini가 11-09, 11-14, 11-16, 11-22 실행에서 한 번도 응답하지 않았다.** 관련성 점수, 카피 생성, 재생성 세 단계 모두 120초 타임아웃이나 504 `DEADLINE_EXCEEDED`였다.
- 설계 의도는 "Gemini(무료) 1순위, Haiku는 장애 때만 쓰는 폴백"이었다. 실제로는 Haiku가 매번 생성하고 있었다. 그 결과 두 가지 문제가 생겼다.
  - **시간 낭비**: 호출할 때마다 Gemini를 120초 기다린다. 이번 실행 8분 11초 중 6분 이상이 대기였다.
  - **숨은 단일 장애점**: "폴백"이라는 이름 때문에 Haiku 키가 보조 수단처럼 보였다. 실제로는 Haiku 키가 하나라도 깨지면 실행 전체가 멈추는 상태였다. 11-16 실패가 바로 그 경우다.

#### 대안 비교

| 안 | 장점 | 단점·위험 | 구현 비용 |
| --- | --- | --- | --- |
| (a) 그대로 둔다 | 변경 없음, Gemini가 살아나면 무료 | 매 실행 6분 이상 대기, 상황 그대로 | 0 |
| (b) 점수 묶음 크기(30건) 축소 | Gemini를 계속 1순위로 쓸 수 있음 | 단건 카피 생성도 504였다 → 묶음 크기가 원인이 아니라서 효과가 없을 것 | 작음 |
| (c) Haiku 1순위 + Gemini 폴백, 순서를 설정값으로 | 대기 제거, 폴백 구조 유지, 한 줄로 되돌릴 수 있음 | 주 1회 몇십~몇백 원 비용 | 중간 (양쪽 앱, 판정 규칙 추가) |
| (d) Haiku만 남기고 Gemini 제거 | 코드가 가장 단순 | 폴백이 사라짐, 멀티 프로바이더 구조를 버림 | 작음 |

#### 결정과 이유
- **(c)를 택했다.** 원래 폴백 계획의 주 근거는 비용이 아니라 가용성이었다(`llm-provider-fallback-plan.md` §1). 그 근거로 보면 "응답하지 않는 쪽을 1순위로 두는 것"이 가장 나쁜 배치다. 비용은 주 1회 실행이라 무시할 만하다.
- (b)는 단건 호출도 실패한다는 로그가 반증이라 버렸다. (d)는 Haiku 장애 때 대안이 없어지고, Gemini가 회복되면 다시 쓸 여지도 사라져서 버렸다.
- 폴백 판정 규칙의 원칙은 유지했다. **일시적 오류만 폴백하고, 우리 쪽 문제(401·400·스키마)는 즉시 실패한다.** 11-16처럼 키가 무효일 때 Gemini로 조용히 넘어가 버리면, 키 문제를 Gemini 무응답이 덮어 버릴 수 있다.

#### 구현·결과
- `LLM_PRIMARY`(`haiku` 기본 | `gemini`)로 순서를 정한다. 잘못된 값은 시작할 때 실패한다.
- 프로바이더별 폴백 판정을 둔다.
  - Haiku: 429/500/529를 3회 재시도한 뒤 실패하거나, 시간 초과(`APIConnectionTimeoutError`)면 폴백
  - Gemini: 기존 규칙 그대로
- 기존 Gemini 전용 분기를 "후보 목록을 순서대로 시도하는 루프"로 바꿨다. 한 번 폴백한 프로바이더는 그 실행 동안 건너뛴다. 대상은 benefit-collector의 점수 배치와 content-generator의 재생성이다.

  ```js
  for (let i = 0; i < candidates.length; i += 1) {
    provider = candidates[i];
    try { result = await call[provider](request); break; }
    catch (err) {
      const next = candidates[i + 1];
      if (!next || !shouldFallBack(provider, err)) throw err; // 401 등은 그대로 실패
      unavailable.add(provider);
    }
  }
  ```
- 테스트에서 프로바이더 호출을 바꿔 끼울 수 있게 `generateJson(request, { order, call })`로 주입점을 열었다. 추가한 테스트는 4개다: 순서 파싱, Haiku 판정, "529 후 폴백, 다음 호출은 1순위 건너뜀", "401은 폴백 안 함".
- 검증
  - benefit-collector 테스트 31개, content-generator 테스트 33개 모두 통과
  - 실제 API로 content-generator 샘플을 생성했다. Gemini 대기 없이 `Claude(claude-haiku-4-5)`가 바로 생성했고, fact-check를 통과했다(2회 생성).
  - benefit-collector 관련성 점수는 실제 API로 **돌리지 않았다**. 11-23 예약 실행 로그로 확인할 예정이다.
- `.meta.json`의 `fellBack` 의미가 "Gemini가 아닌 쪽이 생성"에서 "1순위가 아닌 쪽이 생성"으로 바뀌었다. 계획서에 그렇게 적어 두었다.
- 참고: `_docs/llm-provider-fallback-plan.md` §7, 커밋 `e25ca5a`

#### 배운 점
- 폴백은 "얼마나 자주 발동하는지"를 봐야 한다. 매번 발동하는 폴백은 이미 1순위다. 로그에 프로바이더를 남기도록 설계해 둔 덕분에(09-27 결정) 이 패턴을 근거를 갖고 판단할 수 있었다.
- 우선순위를 코드에 박아 두지 않고 설정값으로 두면, 외부 서비스 상태가 바뀔 때 코드 변경 없이 대응할 수 있다.

## 🐛 발생한 문제 & 해결

### 문제 1: 11-16 주간 실행이 401로 실패
- **증상**: `benefits-weekly` 3분 만에 실패, `invalid x-api-key`
- **영향**: 11-16 회차 미생성, `relevance-cache` 미저장 → 캐시 복원 확인이 한 주 밀림
- **원인 추적**: 실행 목록 → 실패 단계 로그 → Gemini 타임아웃 후 Haiku 401 확인. 카테고리 순환 자체는 정상이었다
- **원인**: Secret 키 무효(확정). 무효가 된 경위는 추정(예전 키를 정리하다 함께 삭제)
- **해결**: 새 키 발급 → Secret 갱신 → 수동 실행 성공
- **재발 방지**: 키 이름에 용도 명시. 실패 알림은 아직 없음
- **상태**: 해결 (알림은 미해결)

### 문제 2: 같은 혜택에서 "491개"가 반복해서 fact-check에 걸림
- **증상**: Actions 실행과 로컬 실행 모두 `gov24:149200005023`의 `details`에서 "원문에 없는 숫자 491개"가 나왔다. 재생성하면 통과한다
- **영향**: 매번 LLM 호출 1회 추가
- **원인**: 미확인. LLM이 매번 같은 숫자를 만드는 걸 보면, 원문에 비슷한 표현(예: 다른 단위)이 있을 가능성이 있다. 원문은 아직 보지 않았다
- **상태**: 미해결 — 계획서 §2.3("100분의 N")과 같은 종류인지 확인 필요

### 문제 3: 실패 알림이 없어 6일 동안 몰랐다
- **증상**: 11-16 실패를 11-22에 진행 상황을 점검하다가 발견
- **상태**: 미해결 — 11-14에 이어 두 번째. 다음 작업 1순위

## 💡 배운 점 / 메모

- "매번 발동하는 폴백은 1순위다." 폴백 경로의 비밀값·한도·비용은 1순위와 같은 수준으로 관리해야 한다.
- 실행 로그를 처음부터 읽기보다 `gh run view --log-failed`로 실패한 단계만 보면 원인까지 몇 분이면 간다.
- 단계 하나가 실패하면 그다음 단계(캐시 저장)의 확인 일정까지 밀린다. 검증 계획을 세울 때 "앞 단계가 실패하면 어떻게 되는가"도 적어 두자.
- Anthropic SDK의 시간 초과는 상태 코드 없이 `APIConnectionTimeoutError`로 온다. 상태 코드만 보는 판정으로는 놓친다.
