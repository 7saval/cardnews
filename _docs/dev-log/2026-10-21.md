## ✅ 완료한 작업

### 1. 발행 이력 갱신 방식 결정 — (b) "워크플로는 결과물만, 이력은 게시 후 사람이 기록"

- 발행 이력(`apps/benefit-collector/data/published.json`)은 ① 다음 수집에서 그 혜택을 빼고 ② 카테고리 순환 순서를 정한다. 그래서 **"실제로 인스타에 올라간 혜택"**과 정확히 맞아야 한다
- 검토한 두 방식:

| | (a) 워크플로가 이력을 직접 커밋 | (b) 결과물만 올리고 게시 후 직접 기록 |
|---|---|---|
| 기록 시점 | 렌더 성공 시 | 사람이 게시한 뒤 `mark-published` |
| 검수 탈락·게시 건너뜀 | 이력에 남아 혜택이 영영 후보에서 빠짐, 카테고리도 넘어감 | 아무것도 안 하면 다음 주 그대로 다시 나옴 |
| 저장소 권한 | 쓰기 필요, 로컬 작업과 이력 파일 충돌 가능 | 읽기만 |
| 실수했을 때 | 조용히 후보가 사라져 알아채기 어려움 | `mark-published`를 잊으면 같은 회차가 다시 만들어질 뿐 |

- **(b)로 결정.** publisher(자동 게시)가 아직 README뿐이라 워크플로는 "게시했는지"를 알 수 없다. 어차피 계획서에 "발행 전 사람 검수"가 있어서, 검수할 때 명령 한 줄이 더해질 뿐
- publisher가 생기면 **게시 API 성공 직후 publisher가 기록** — 그때 이력도 계획대로 Supabase `published_benefits`로 옮긴다
- 참고: `_docs/topic-pivot-benefits-plan.md` §6.5

### 2. `scripts/pipeline.js` 교체

- 맛집 시절 흐름(카피 → 이미지 매칭 → 렌더)을 **수집·선별 → 카피 + fact-check → 렌더**로 교체. 이미지 매칭 단계 제거
- `--collect`면 benefit-collector부터 3단계, 없으면 가장 최근 `*-adopted.json`(또는 `--input`)으로 2단계
- `--series`, `--category`, `--region`, `--count`, `--refresh`는 수집기로 그대로 넘김. 모르는 옵션이나 `--collect` 없이 수집 옵션을 쓰면 즉시 에러
- 수집기가 만든 파일 경로를 파이프라인이 알아야 해서 `collect.js`에 `--out` 추가 (최근 파일을 mtime으로 찾는 방식보다 확실)
- **결과 폴더 하나로 묶기**: `apps/card-renderer/output/benefit/<이름>/`에 카드 PNG + `caption.txt` + `adopted.json`(게시 후 `mark-published`에 넘길 파일) + `scores.json` + `card-news.json`(+ meta). 검수·게시·이력 기록에 필요한 게 한 폴더에 있다
- 끝나면 다음 할 일(`mark-published` 명령)을 출력

### 3. 게시물 캡션 자동 생성 (`apps/content-generator/src/caption.js`)

- 카드에 "원문 링크는 캡션에 ↓"라고 적어 놨는데, (b) 방식은 사람이 직접 게시하므로 캡션 텍스트가 필요했다 — 계획 범위 밖이었지만 카드의 약속을 지키려면 필수
- 카드마다 `정책명 / 혜택 / 대상 / 신청기한 / 원문 링크`, 끝에 "비공식 큐레이션 · 신청 전 원문 공고 확인" 안내와 출처 (계획서 §8 "캡션에 원문 링크와 확인 안내를 고정 문구로")
- **LLM을 거치지 않고** 카드뉴스 JSON의 사실 필드만으로 만든다. 인스타 한도 2,200자를 넘으면 실패
- `generate.js`가 `<이름>.caption.txt`로 같이 저장. 테스트 3개 추가 (content-generator 총 27개)

### 4. 주간 워크플로 `.github/workflows/benefits-weekly.yml`

- 매주 월요일 KST 07:00(`cron: '0 22 * * 0'`) + 수동 실행(시리즈·카테고리·자치구·개수 입력)
- `permissions: contents: read` — 저장소에 쓰지 않는다
- 결과 폴더를 artifact `cardnews-<번호>`로 업로드(30일 보관). 실패하면 `.failed.json`과 점수를 `failed-<번호>`로 올려 원인을 볼 수 있게
- 관련성 점수 캐시(`relevance-cache.json`)를 `actions/cache`로 실행 사이에 이어 씀 — 원문이 안 바뀐 혜택은 LLM에 다시 묻지 않는다 (키는 `run_id`, 복원은 `relevance-` 접두어로 가장 최근 것)
- 우분투 러너에서 카드의 📷·💬가 네모로 나오지 않게 `fonts-noto-color-emoji` 설치
- 필요한 Secrets: `DATA_GO_KR_SERVICE_KEY`, `GEMINI_API_KEY`, `ANTHROPIC_API_KEY`(폴백)

## 🐛 발생한 문제 & 해결

### 문제 1: README·계획서를 고치던 셸 명령이 120초 멈춤

- **원인**: `node -e "..."` 안에 템플릿 리터럴 백틱과 마크다운 코드 펜스(```)를 이스케이프해서 넣다가 따옴표 짝이 깨져 셸이 입력을 기다림. 10-18에도 같은 유형(python 스텁, 인자 없는 `cat`)으로 두 번 멈췄다
- **해결**: 작업을 중단하고 파일이 안 바뀐 것을 `git status`로 확인한 뒤, 파일 편집 도구로 같은 수정을 다시 함
- **참고**: 여러 줄 문서 수정은 셸 한 줄 스크립트로 하지 않는다

### 문제 2: 수동 실행(`workflow_dispatch`) 버튼이 브랜치에서는 안 보임 — 미해결

- **원인**: GitHub은 워크플로 파일이 **기본 브랜치(main)**에 있어야 수동 실행을 띄울 수 있고, 예약 실행(`schedule`)도 기본 브랜치 기준으로만 돈다. 작업은 아직 `7saval/benefits-pivot`에만 있음
- **현재 상태**: 브랜치 push → main 머지 → Secrets 등록 후 수동 실행으로 확인 예정. Phase D 완료 표시는 그때 함

### 문제 3: 워크플로에서 Playwright 설치 명령 경로

- **원인**: 처음엔 저장소 루트에서 `npx --prefix apps/card-renderer playwright install`로 썼는데, `--prefix`로 앱 폴더의 로컬 바이너리를 확실히 잡는지 보장할 수 없었다
- **해결**: `cd apps/card-renderer && npx playwright install --with-deps chromium`으로 변경 (실행 전 수정, 실제 CI 확인은 아직)

## 💡 배운 점 / 메모

- **상태를 기록하는 주체는 그 사실을 아는 쪽이어야 한다.** 렌더 성공은 "게시했다"가 아니다. 자동화 범위가 게시까지 안 닿았으면, 그 경계에서 사람이 기록하는 게 맞다
- 자동화의 실수는 "조용히 틀리는 것"과 "시끄럽게 반복되는 것"으로 나눠 볼 수 있다. (a)는 앞쪽(후보가 소리 없이 사라짐), (b)는 뒤쪽(같은 회차가 다시 나옴) — 뒤쪽이 훨씬 다루기 쉽다
- 파이프라인 결과물은 **다음 사람이 할 일 단위로 묶는다** — 검수(PNG·caption), 게시(PNG·caption), 이력 기록(adopted.json)이 한 폴더에 있으면 artifact 하나로 끝난다
- 사실을 담는 캡션도 카드와 같은 원칙 — LLM이 아니라 코드가 사실 필드로 만든다
- LLM이 "100분의 20"을 매번 "20%"로 바꾸려 한다. fact-check가 매번 잡아서 재생성 1회가 사실상 고정 비용이 됐다 — 프롬프트에 "원문의 분수 표현은 그대로" 규칙을 넣거나 fact-check에 `100분의 N ↔ N%` 정규화를 넣을지 검토
- GitHub Actions 예약·수동 실행은 기본 브랜치 기준이다. 워크플로를 기능 브랜치에서 만들면 머지 전엔 실행해 볼 수 없다
