## ✅ 완료한 작업

### 1. NAVER API HUB 검색 API 활성화

- 기존 키로 지역/웹문서/블로그 검색을 호출해 보니 3개 모두 `401 "요청한 API는 이 Application에서 활성화되어 있지 않습니다"` — 키는 정상, Application에 API가 안 켜진 상태
- NCP 콘솔 **Application Services → NAVER API HUB → Application**에서 기존 Application에 API 추가 → 재호출 시 3개 모두 `200`
- 확인한 조건: 현재 한시적 무료, 검색 API 월 775,000건·키당 50 RPS (NCP 가이드)

### 3. "네이버 지도 업체 사진을 쓰면 안 되나" 재검토

- 업체가 올린 사진은 네이버 안에서 보여주라는 허락이지 제3자 재게시 허락이 아님, 사진 탭엔 방문자 리뷰·블로그 사진도 섞여 있어 사장님조차 권리가 없는 경우가 있음, 출처 표기는 허락을 대신하지 못함, 인스타 저작권 신고 누적 시 계정 제재 위험
- 결론: **"허락받은 사진만 사용" 방향 유지**. DM 한 통이면 되는 저비용 경로라 자동 수집 대비 리스크가 훨씬 작음

### 4. `npm run find-channels` 구현

- `src/find-channels.js` — 흐름 조립, 신뢰도(높음/중간), 체크리스트(MD, DM 템플릿 포함) + 상세(JSON: 근거·건너뛴 이유·실제 요청 URL) 출력
- `src/lib/extract.js` — `<b>` 태그 제거, 주소 정규화, 인스타 계정 추출(게시물/릴스 경로·이메일 제외), 링크 분류(인스타/홈페이지/플랫폼)
- `src/lib/robots.js` — `robots.txt` 파서 직접 구현(RFC 9309: UA 그룹 선택, 가장 긴 매칭 우선·동률이면 Allow, `*`/`$`, 빈 Disallow)
- `src/lib/polite-fetch.js` — 크롤링 규칙을 **코드로 강제**: 네이버·카카오·다음·인스타·페이스북 도메인 요청 거부, UA 명시, 같은 호스트 1초 간격, 타임아웃 10초, 2MB 제한, 리다이렉트마다 차단 도메인·`robots.txt` 재확인, `robots.txt` 리다이렉트 5회까지 추적, 확인 불가(5xx/오류)면 불허
- `src/lib/naver-search.js` — 지역·웹문서·블로그 호출
- 실행 결과(8곳): 돌산등대집 @dolsanhouse(높음, 지역검색+블로그), 오징어풍경 `opoong.com`(중간), 나머지 6곳은 네이버 지도/검색 수동 링크. **크롤링 요청은 `opoong.com/robots.txt`, `opoong.com/` 2건뿐** — 조사 결과와 일치
- 오징어풍경 홈페이지에 인스타 링크가 정말 없는지 별도 확인 → 없음 (`insta`로 걸린 건 JS의 `instanceof`)
- 참고 파일: `apps/image-matcher/src/find-channels.js`, `apps/image-matcher/src/lib/*`

### 5. 사진 폴더 구조 재설계 (10-01)

사용자 제안("주제별 폴더 밑에 가게 폴더")을 검토한 뒤 다음으로 확정:

```
images/
├── places/<가게>/            가게 단위 — 허락은 가게별로 받으므로 여러 주제에서 재사용
│   ├── 1.jpg, credit.txt
│   └── place.json           --init이 가게 이름·주소 기록
├── topics/<주제>/_cover/     주제별 커버 (<주제> = series_title)
└── _cta/                    맛수집 공통 CTA 배경 (사용자 결정: 브랜드 배경을 한동안 고정 사용)
```

- 가게를 주제 밑에 두면 새 주제마다 같은 가게 사진·출처를 복사해야 하고 어긋나기 쉬움 → 가게 단위가 "허락받은 가게 목록" 역할도 함
- 기존 구조의 문제 발견: `_cover`가 전 주제 공용이라 다음 주제에도 같은 커버가 들어감 → 주제별로 분리
- **동명 가게 방지**: 이름만으로 매칭하면 다른 동네 "보물섬"에 사진이 들어갈 수 있음 → `place.json` 주소와 카드 주소를 도로명 기준으로 대조, 이름이 같고 주소가 다르면 미사용. `--init`은 동명 다른 가게가 있으면 `보물섬 (강남구)`처럼 구를 붙여 폴더 생성
- `src/lib/place-folders.js`로 폴더 선택 로직 분리 + 단위 테스트, `match.js` 재작성, card-renderer `/__images` 미들웨어를 다단계 경로(`places/<가게>/<파일>`) 지원으로 변경
- 검증: 서초구 주소의 `보물섬` 폴더(사진·출처 있음)를 미리 만들어 두고 실행 → 강남 보물섬 카드엔 **안 들어감**, `보물섬 (강남구)` 폴더 별도 생성 확인. 주제 커버·공통 CTA 렌더링 확인. 테스트 파일 정리

## 🐛 발생한 문제 & 해결

### 문제 1: 자동 모드에서 명령 실행이 반복적으로 막힘
- **원인**: 자동 모드의 서버 쪽 안전성 분류기가 판정 대신 오류(`gave no verdict (error)`)를 반환 — 명령이 위험하다고 거부된 게 아니라 검사 서비스 일시 장애. 파일 읽기·검색은 이 검사를 안 거쳐서 계속 됨
- **해결**: 자동 모드 해제 후 명령마다 사용자 승인 방식으로 진행
- **참고**: 그 사이 확인용 스크립트를 scratchpad에 파일로 만들어 두고 이어서 실행

### 문제 2: NAVER API HUB 가이드에 "기존 Application에 API 추가" 절차가 명시돼 있지 않음
- **원인**: 가이드의 Application 수정 항목은 "필요한 정보를 수정한 다음 [저장]"까지만 기술. 문서 요약 도구는 "삭제 후 재등록해야 한다"고 추론했지만 원문 근거 없음(소개 페이지는 "별도 신청 없이 필요한 API를 선택해 바로 사용")
- **해결**: 수정으로 먼저 시도하고, 안 되면 새 Application을 전체 API로 등록(기존은 새 키 확인 후 삭제)하는 두 경로로 안내 → 수정으로 해결됨
- **참고**: 요약 도구의 추론을 사실로 전달하지 않도록 주의

### 문제 3: 계획서 가정(지역검색 `link`가 1순위 소스, 웹문서로 인스타 발견)이 실제 데이터와 다름
- **원인**: 계획 단계에선 API 문서 설명("업체, 기관의 상세 정보 URL")만 보고 판단
- **해결**: 구현 전 8곳 조사로 소스별 실제 효용을 측정하고 설계·완료 기준을 수정 (완료한 작업 2)

### 문제 4: `place.json` 없는 폴더에서 `addressKey(null)` TypeError
- **원인**: `addressKey(address = '')`의 기본값은 `undefined`일 때만 적용되고 `null`엔 적용 안 됨
- **해결**: 문자열이 아니면 `null` 반환하도록 수정, 테스트 케이스 추가 — 단위 테스트가 잡아줌

### 문제 5: 경로 조작 테스트에서 `200` 응답이 나와 뚫린 것처럼 보임
- **원인**: `Invoke-WebRequest`가 `../`를 보내기 전에 정리해서 실제로는 `/package.json`(Vite 기본 서빙)을 요청한 것
- **해결**: `curl --path-as-is`로 `../`를 그대로 보내 재확인 → 3가지 모두 `404`

## 💡 배운 점 / 메모

- **구현 전에 실제 데이터로 한 번 찔러보는 조사**가 설계를 크게 바꿨다 — 계획서만 믿고 만들었으면 웹문서·블로그 오탐 후보로 엉뚱한 사람에게 DM을 보내는 도구가 됐을 것
- 탐지율이 낮을 때 억지로 올리기보다 "찾은 건 근거와 함께, 못 찾은 건 사람이 빨리 찾게"로 완료 기준을 바꾸는 게 현실적이었다
- "하지 않는다"는 원칙(플랫폼 도메인 요청 금지)은 문서가 아니라 코드(`polite-fetch.js` 차단 목록)로 강제하고, 실제 요청 URL 로그로 증명 가능하게 두는 게 좋다
- 폴더 구조는 **권리가 부여되는 단위**(가게별 허락)를 따라가야 재사용과 관리가 쉬워진다. 주제별 자원(커버)과 브랜드 공통 자원(CTA)은 따로
- 이름 기반 매칭엔 동명 이슈가 따라온다 — 두 번째 키(주소)를 함께 저장해두면 코드가 잘못된 매칭을 막아준다
- JS 기본 매개변수는 `null`을 막지 못한다. 외부 파일에서 읽은 값은 타입을 직접 확인할 것
- 경로 조작 테스트는 클라이언트가 경로를 정규화하지 않게(`curl --path-as-is`) 해야 의미가 있다
- 문서 요약 도구가 "문서에 없다"를 "불가능하다"로 추론하는 경우가 있다 — 원문 근거와 추론을 구분해서 전달할 것
