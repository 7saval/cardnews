## ✅ 완료한 작업

### 1. 예약 워크플로 실패 알림

#### 배경·문제 정의
- 이 프로젝트에는 예약 실행이 두 개 있다. 매일 성적을 기록하는 `insights-daily`, 매주 카드뉴스를 만드는 `benefits-weekly`.
- 둘 다 실패해도 아무도 알려 주지 않았다.
  - `insights-daily`는 2026-09-28부터 **7주** 동안 매일 실패했다. 자동화 전/후 비교의 베이스라인 데이터가 그만큼 비었다.
  - `benefits-weekly`는 11-16 실패를 **6일 뒤**(11-22)에 진행 상황을 점검하다 발견했다.
- 두 번 모두 내가 우연히 실행 목록을 열어서 알았다. 자동화를 늘릴수록 "멈춘 줄 모르는" 위험도 커진다.

#### 조사
- GitHub 기본 이메일 알림은 왜 안 왔나: 예약 실행 실패 알림은 **cron을 마지막으로 수정한 사용자**에게만 가고, 계정 알림 설정에 따라 꺼져 있을 수 있다. 이번처럼 놓치기 쉬운 경로라 믿을 만한 알림이 아니라고 판단했다.
- 알림에 무엇이 들어가야 하는지는 11-16 실패를 기준으로 정했다. 원인은 로그 수백 줄 중 `401 invalid x-api-key` 한 줄이었다. **실패 단계 이름 + 원인 줄**이 알림에 바로 보여야 한다.

#### 대안 비교 — 알림 채널

| 안 | 장점 | 단점·위험 | 구현 비용 |
| --- | --- | --- | --- |
| **GitHub 이슈 (택)** | 추가 Secret 없음, 앱 푸시·이메일로 옴, 열림/닫힘이 곧 "지금 고장 났는가" 상태, 기록이 남음 | 공개 저장소라 이슈도 공개 | 중간 |
| Discord / Slack 웹훅 | 휴대폰 푸시가 가장 빠름 | 웹훅 URL Secret 관리, 상태(고장 중/복구)를 따로 추적해야 함 | 작음 |
| GitHub 기본 이메일 설정만 | 코드 변경 없음 | 예약 실행은 cron 수정자에게만 감, 이미 두 번 놓침 | 0 |

#### 대안 비교 — 어디에 붙일까

| 안 | 장점 | 단점·위험 |
| --- | --- | --- |
| 각 워크플로 끝에 `if: failure()` 단계 추가 | 단순 | 감시 대상 워크플로에 `issues: write` 권한이 필요 → 지금의 "읽기 전용" 원칙이 깨짐. 시작 자체가 실패하면 그 단계도 안 돈다 |
| **별도 워크플로 + `workflow_run` 트리거 (택)** | 기존 워크플로는 그대로, 권한은 알림 워크플로에만. 시간 초과·시작 실패도 잡음 | 기본 브랜치(main)의 파일만 쓰여서 브랜치에서는 테스트할 수 없음 |

#### 결정과 이유
- **GitHub 이슈 + 별도 `notify-failure` 워크플로**로 정했다.
- 이슈를 "알림 한 번"이 아니라 **고장 상태**로 쓴다.
  - 처음 실패 → `[실패] <워크플로>` 이슈를 만들고 저장소 주인에게 할당한다. 할당이 곧 알림이다.
  - 연속 실패 → 새 이슈 대신 같은 이슈에 댓글을 단다. `insights-daily`는 매일 돌아서, 고장 난 채로 두면 하루에 이슈가 하나씩 쌓인다. 7주였다면 49개다.
  - 다음 성공 → "복구됨" 댓글을 달고 자동으로 닫는다. 열린 이슈가 있으면 지금 고장 중이라는 뜻이 된다.
- 사람이 수동으로 취소한 실행은 알리지 않는다. 내가 한 일을 나에게 알릴 필요는 없다.

#### 구현·결과
- `.github/workflows/notify-failure.yml`
  - 트리거: `workflow_run` (`benefits-weekly`, `insights-daily`, `completed`)
  - 권한: `issues: write`, `actions: read`(실패 단계·로그 조회). 감시 대상 워크플로의 권한은 그대로
  - 본문: 워크플로, 결과, 시작 시각(KST), 트리거, 실행 링크, **실패한 job·단계 이름**, **로그 끝부분**
- 로그 끝부분은 원인 줄만 남도록 정리한다.

  ```bash
  gh run view "$RUN_ID" --log-failed \
    | sed -E 's/^[^\t]*\t[^\t]*\t(\xEF\xBB\xBF)?[0-9TZ:.-]+ //; s/\x1b\[[0-9;]*m//g' \
    | awk '/##\[group\]/{g=1} /##\[endgroup\]/{g=0; next} !g' \
    | grep -B25 -m1 -E '##\[error\]'
  ```

- **검증: push 전**
  - YAML 파싱(`yaml` 패키지), 단계별 셸 스크립트를 꺼내 `bash -n`
  - YAML 블록이 들여쓰기를 걷어낸 뒤 heredoc 본문과 `EOF`가 0열에 오는지 확인
  - 11-16에 실제로 실패한 실행(run 43787530859)으로 로그 정리를 돌려, `✘ 수집 실패: 401 …` 줄이 나오는지 확인
- **검증: push 후 실제 실행.** `insights-daily`를 날짜 `bad`로 수동 실행했다. 날짜 형식 검사에서 실패해 API·DB를 건드리지 않는다.

  | 경로 | 실행 | 결과 |
  | --- | --- | --- |
  | 처음 실패 | 45038541280 | 이슈 #1 생성, 주인에게 할당, 실패 단계와 원인 줄 포함 ✅ |
  | 연속 실패 | 45038717931 | 새 이슈 없이 #1에 "또 실패했습니다" 댓글 ✅ |
  | 복구 | 45038794557 (날짜 없이 실행) | #1에 "✅ 복구됨" 댓글, 자동으로 닫힘 ✅ |

- 참고 커밋: `32b2339`(알림 워크플로), `2bf7d25`(로그 정리 개선), `0461286`(문서 반영)

#### 배운 점
- 자동화의 마지막 단계는 "실패했을 때 사람에게 닿는 경로"다. 배치를 만들 때 알림을 같이 만들어야 한다.
- 알림은 "보냈다"보다 "지금 고장 중인가"를 표현해야 한다. 상태가 있는 알림(열림/닫힘)은 연속 실패에도 소음이 쌓이지 않는다.
- 일부러 실패시킬 수 있는 안전한 입력(`date=bad`)이 있으면 알림 같은 운영 코드도 실제 환경에서 검증할 수 있다.

### 2. 만들고 안 올린 회차(`cardnews-6`)의 처리 확인

#### 배경
- 11-22에 수동 실행으로 `cardnews-6`(고용·창업 5건)을 만들었지만 인스타에 올리지 않았다. 다음 자동 수집에서 같은 혜택이 "중복으로" 들어오는지가 궁금했다.

#### 확인
- 수집기가 후보에서 빼는 기준은 `data/published.json`뿐이고, 이 파일은 `mark-published`로만 바뀐다. 지금 기록은 11-14 생활안정 5건뿐이다.
- 그래서 오늘 예약 실행도 고용·창업을 다시 고른다. 점수 캐시와 고정된 순위 규칙 때문에 대부분 같은 5건이 나올 것이다(문구는 다를 수 있음).
- 이건 10-21에 정한 **"발행했을 때 기록한다"** 설계가 의도한 동작이다. 만들기만 한 회차의 혜택이 후보에서 사라지지 않는다.
- 진짜 중복 위험은 **두 회차를 모두 게시하는 것**뿐이다. `mark-published`를 두 번 실행해도 `history.js`가 `source_id`로 거르기 때문에 기록은 중복되지 않는다.

#### 결정
- `cardnews-6`과 오늘 나올 `cardnews-7`을 비교해 하나만 게시하고, 그 폴더의 `adopted.json`으로 한 번만 기록한다.

## 🐛 발생한 문제 & 해결

### 문제 1: 첫 알림 이슈의 로그가 지저분함
- **증상**: 이슈 #1의 로그 칸에 단계 스크립트 원문, 터미널 색상 코드(`^[[36;1m`), 첫 줄 앞의 BOM, env 목록이 섞여 원인 줄이 묻혔다
- **원인 추적**: `--log-failed` 원문을 보니 ① 첫 줄에만 BOM이 붙어 타임스탬프 제거 정규식이 안 맞았고, ② 단계 스크립트가 `##[group]`~`##[endgroup]` 안에 색상 코드와 함께 찍혀 있었다. 처음엔 `##[group]` 줄만 지웠는데, 그 사이 내용까지 빼야 했다
- **원인**: 확정 (로그 원문 확인)
- **해결**: BOM 선택 매칭, 색상 코드 제거, group 구간을 `awk`로 통째로 제거, 보조금24 페이지 진행 줄 제외, 25줄로 축소. 두 실패 실행(11-16, 11-23 테스트)으로 다시 확인
- **재발 방지**: 테스트 방법(`date=bad`)을 워크플로 주석에 남김
- **상태**: 해결
