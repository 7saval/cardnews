  4. 상위 `--top`개 주제를 "채택"해서 `content-generator`의 `--input`에 바로 넣을 수 있는 텍스트 파일 생성(+ 감사용 전체 결과 JSON)

- 참고 파일: `apps/research-collector/src/collect.js`, `apps/research-collector/data/topics.json`, `npm run collect`

### 2. content-generator의 Gemini SDK 재시도 버그 원인 분석 및 수정

- research-collector 산출물을 `content-generator`에 실제로 넣어보다가 `TypeError: unusable` 에러 발견 (기존 코드 주석에 "재시도를 꺼도 재현되는 버그"로만 기록돼 있던 것)
- SDK 소스(`node_modules/@google/genai/dist/node/index.mjs`)를 직접 열어서 원인 추적: `ai.interactions.create()`(신형 "next-gen" 엔드포인트)는 요청 본문을 `ReadableStream`으로 만드는데, 공통 재시도 레이어(`ClientSDK._do`)가 실패 시 원본 `Request`를 다시 `.clone()`해서 재시도함 → 스트림 바디는 한 번 소비되면 다시 clone 불가 → `TypeError: unusable`
- 구형 안정 엔드포인트인 `ai.models.generateContent()`(요청 본문이 일반 JSON, 스트림 아님)로 전환해서 근본 해결. `retryOptions.attempts: 1`로는 막을 수 없던 문제였음(clone 자체가 재시도 횟수와 무관하게 호출됨)
- 전환 후엔 실제 API 에러(503 과부하, 429 할당량 초과, 404 모델명 오류)가 그대로 올라오는 걸로 재현 방식이 바뀌어서, 버그가 사라졌다는 걸 역으로 확인
- 안전하게 재시도할 수 있게 됐으니 `withRetry()` 헬퍼도 같이 추가(429/503 지수 백오프 최대 3회)
- 참고 파일: `apps/content-generator/src/generate.js`

### 3. Gemini 무료 티어 일일 할당량 소진 경험 → Claude Haiku 폴백 논의

- 2번 수정을 검증하려고 반복 호출하다가 `gemini-3.8-flash` 무료 티어의 **일일 할당량(20건/일)**을 그날 안에 다 써버림(`429 RESOURCE_EXHAUSTED`, quotaId `GenerateRequestsPerDayPerProjectPerModel-FreeTier`)
- 이 경험을 계기로 "할당량 소진 시 Claude Haiku로 자동 전환"을 검토
- 처음엔 "비용 절감"을 근거로 제시했으나, claude-api 스킬로 Haiku 4.5 실제 가격(입력 $1/출력 $5 per 1M 토큰)을 확인해서 계산해보니 카드뉴스 1건당 약 8~13원 수준 — 절감 효과 자체는 미미하다는 걸 확인. 근거를 재정리해서 **가용성(무료 한도로 파이프라인이 멈추는 걸 막음) > 멀티 프로바이더 자동화 서사(포트폴리오) > 비용 절감(약한 보조 근거)** 순으로 확정

### 4. LLM 프로바이더 폴백 구현 계획서 작성

- `_docs/llm-provider-fallback-plan.md` 신규 작성
- 핵심 설계 원칙: Gemini가 항상 1순위(무료·검증된 경로), Haiku는 429/503(한도 소진·과부하)일 때만 개입, 스키마 검증 실패 등 우리 쪽 버그는 폴백하지 않고 즉시 실패시켜서 폴백이 진짜 버그를 가리지 않게 함, 사용된 provider는 항상 로그로 남김

### 5. 계획대로 폴백 구현

- `generate.js`의 Gemini 호출부를 `generateWithGemini(rawMaterial)`로 분리, `generateWithHaiku(rawMaterial)` 신규 작성
- `withRetry()`가 프로바이더별로 다른 재시도 대상 상태코드를 받도록 수정 — Gemini(429/503)와 Anthropic(429/500/529 overloaded)의 재시도 대상 코드가 다르다는 걸 claude-api 스킬의 `error-codes.md`로 확인하고 반영(Anthropic은 503이 아니라 529를 씀)
- Haiku의 구조화 출력은 claude-api 스킬의 `typescript/claude-api/tool-use.md`를 먼저 읽고 결정 — 추측하지 않고 문서화된 `client.messages.parse({ output_config: { format: zodOutputFormat(schema) } })`(Zod 기반, 권장 경로) 사용
- 이를 위해 `prompt.js`에 기존 JSON Schema(`CARD_NEWS_RESPONSE_SCHEMA`, Gemini용)와 병행해서 Zod 스키마(`CARD_NEWS_ZOD_SCHEMA`, Haiku용)를 추가 — 필드 변경 시 두 스키마를 같이 고쳐야 함을 주석으로 명시
- `@anthropic-ai/sdk`(^0.128.0), `zod`(^4.6.5) 의존성 추가, `.env`/`.env.example`에 `ANTHROPIC_API_KEY`/`ANTHROPIC_MODEL` 추가
- 결과 저장 시 어느 provider가 실제로 생성했는지 사이드카 메타 파일(`<output>.meta.json`)에 기록 — `shared/schemas/card-news.ts` 스키마 자체는 건드리지 않음
- 참고 파일: `apps/content-generator/src/generate.js`, `apps/content-generator/src/prompt.js`

### 6. 폴백 동작 실검증

- 마침 그날 소진된 Gemini 할당량을 이용해 폴백 트리거 로직을 실제 상황으로 검증: Gemini 429 → 재시도 3회 소진 → Haiku로 자동 전환하는 흐름이 로그로 정확히 확인됨
- 사용자에게 `ANTHROPIC_API_KEY` 요청 → 키 입력 후 재실행 → Haiku가 실제로 카드뉴스 JSON(카드 8개)을 생성하고 `assertValidCardNewsData` 검증을 통과하는 것까지 확인
- 여기서 그치지 않고 이 JSON을 `card-renderer`로 렌더링해서 PNG 10장(cover 1 + content 8 + cta 1)까지 정상 출력되는 걸 확인 — research-collector → content-generator(폴백 포함) → card-renderer 전체 파이프라인이 끊기지 않음을 이미지로 직접 확인
- 메타 파일에 `{ provider: "haiku", model: "claude-haiku-4-5", fellBack: true }`가 정확히 기록되는 것도 확인

## 🐛 발생한 문제 & 해결

### 문제 1: Gemini `ai.interactions.create()` 호출 시 `TypeError: unusable`
- **원인**: 이 엔드포인트가 요청 본문을 `ReadableStream`으로 구성하는데, SDK의 공통 재시도 레이어가 실패 시 원본 `Request`를 `.clone()`해서 재시도를 시도함 — 스트림 바디는 한 번 소비되면 다시 clone할 수 없어 에러가 남. `retryOptions.attempts: 1`로 재시도 횟수를 줄여도 clone 자체는 호출되므로 해결이 안 됐던 것
- **해결**: 요청 본문이 일반 JSON인 구형 안정 엔드포인트 `ai.models.generateContent()`로 전환. 이후 재시도가 안전해져서 `withRetry()` 헬퍼도 추가
- **참고**: `apps/content-generator/src/generate.js`

### 문제 2: Gemini 무료 티어 일일 할당량(20건/일) 소진
- **원인**: 문제 1을 검증하려고 같은 모델(`gemini-3.8-flash`)로 반복 호출하다가 하루치 무료 요청 수를 다 씀
- **해결**: 즉시 해결하기보다, 이 상황 자체를 계기 삼아 Claude Haiku 폴백을 설계·구현. 오늘 소진된 할당량을 오히려 폴백 트리거 로직의 실제 테스트 조건으로 활용함
- **참고**: `_docs/llm-provider-fallback-plan.md`

### 문제 3: Gemini와 Anthropic의 "재시도해도 되는" 상태코드가 서로 다름
- **원인**: Gemini는 과부하를 503으로 응답하지만, Anthropic은 과부하를 529(`overloaded_error`)로 응답함(500도 재시도 대상). 두 프로바이더에 같은 재시도 상태코드 집합을 쓰면 Anthropic 쪽에서 재시도가 안 먹힐 뻔했음
- **해결**: claude-api 스킬의 `shared/error-codes.md`로 정확한 값을 확인한 뒤 `GEMINI_RETRYABLE_STATUS`(429/503)와 `ANTHROPIC_RETRYABLE_STATUS`(429/500/529)를 분리해서 정의
- **참고**: `apps/content-generator/src/generate.js`

## 💡 배운 점 / 메모

- SDK가 "재시도 횟수를 줄이면" 해결될 것 같은 버그도, 재시도 로직 자체(예: 요청 clone)가 재시도 여부와 무관하게 항상 실행되는 경우가 있다 — 옵션값 조정보다 SDK 소스를 직접 열어서 어느 레이어에서 실패하는지 확인하는 게 더 빨랐음
- "무료 API는 공짜"라는 생각으로 반복 테스트하면 일일 할당량을 순식간에 소진할 수 있다 — 특히 디버깅/프롬프트 튜닝처럼 짧은 시간에 여러 번 호출하는 작업일수록 할당량을 의식해야 함
- 프로바이더를 추가할 때 "비슷한 기능이니 같은 상수를 재사용해도 되겠지"라는 가정이 위험할 수 있다 — HTTP 상태코드처럼 표준화된 값도 벤더마다 의미가 다르게 쓰이는 경우가 있음(Gemini 503 vs Anthropic 529)
- 비용 절감을 근거로 제시하기 전에 실제 가격으로 계산해보니, "방향은 맞지만 효과는 작다"는 걸 확인할 수 있었다 — 근거를 감으로 내세우지 않고 숫자로 검증하는 습관이 결정의 우선순위를 더 명확하게 정리해줌
- 폴백처럼 "정상 케이스에서는 발동 안 하는" 로직은 일부러 장애를 만들기 어려운 경우가 많은데, 오늘은 마침 실제로 발생한 할당량 소진 상황을 그대로 테스트 조건으로 활용할 수 있었음 — 우연이지만 실제 장애 상황으로 검증한 셈이라 신뢰도가 더 높음
