### 6. 일일 수집 배치 `collect.js` 구현 (`npm run collect`)

- `test-insights.js`의 조회 로직을 가져와 `daily_insights`에 `date` 기준 upsert (`research-collector/collect.js`의 CLI 패턴 따름)
- **집계 기준을 "KST 기준 어제 하루"로 고정**: 인사이트 호출에 `since/until`(KST 00:00~24:00 unix ts)을 명시. 기본값(최근 1일)에 맡기면 실행 시각에 따라 구간이 흔들리기 때문
- `followers_count`는 계정 필드라 과거 값을 조회할 수 없고 항상 "실행 시점" 스냅샷 → 크론을 자정 직후(KST 00:30)로 잡아 "어제 마감 값"에 최대한 가깝게 함
- `posts_count_today`: `/media`(최신순)를 페이지네이션하며 `timestamp`가 구간 안인 게시물 수를 셈, 구간 시작보다 오래된 게시물이 나오면 조기 종료
- `is_automated`: Phase 4 전이라 `false` 고정
- 옵션: `--date YYYY-MM-DD`(재수집), `--dry-run`(DB 쓰기 없이 출력)
- 검증: dry-run → 실제 적재 → 같은 날짜 재실행(PK 충돌 에러 없이 덮어씀 = upsert 정상) 순서로 확인
- 참고 파일: `apps/insights-collector/src/collect.js`

### 8. 파이프라인 오케스트레이션 스크립트 (`npm run pipeline`)

- 루트에 `scripts/pipeline.js` + 루트 `package.json`(스크립트만, 의존성 없음) 추가. 계속 이월되던 "content-generator → card-renderer 수동 연결" 해소

### 9. Gemini 폴백 로그 개선 + 브라우저 미리보기

- 폴백 시 상태 코드만 찍히고 Gemini 에러 본문이 버려져서, 오늘 503의 정확한 사유를 로그로 알 수 없었음 → 경고에 에러 원문을 함께 출력

- Playwright 렌더 경로(`?card=`, `window.__RENDER_DATA__`)는 건드리지 않음. 경로 조작(`../`) 요청은 404로 차단되는지 직접 확인
- 참고 파일: `apps/card-renderer/vite.config.ts`, `apps/card-renderer/src/App.tsx`

### 11. `apps/image-matcher` 구현 (허락받은 사진 → 카드 반영)

- `src/match.js`(`npm run match`): `images/<장소명>/`의 사진(파일명 순 첫 장)과 `credit.txt` 첫 줄(출처)을 카드 JSON의 `image_url`/`image_credit`에 반영

  - 재실행 시 이전 매칭이 남지 않도록 항상 덮어씀
- 스키마에 `image_credit` / `cover_image_credit` / `cta_card.image_credit` 추가, 렌더러에 `ImageCredit` 컴포넌트(워터마크 아래 `📸 @출처`)

- 파이프라인을 **카피 생성 → 사진 매칭 → 렌더링** 3단계로 확장 (사진이 없어도 placeholder로 끝까지 진행)

- 검증: `pipeline-test.json` 복사본 + 더미 사진으로 매칭(출처 있음 ✔ / 출처 없음 → 미사용 / 커버 대체)과 렌더링 PNG(배경 + 출처 표기)를 직접 확인 후 테스트 파일 정리

### 문제 2: 앱 역할 확인 도중 Graph API Explorer 토큰 발급 과정에서 "Invalid platform app" 에러 발생
- **원인**: 정확한 원인은 특정하지 못함. 공식 문서/웹서치 모두 이 에러에 대한 명확한 설명이 없었음
- **해결**: 이후 앱 설정을 다시 정리하고 토큰을 재발급하는 과정에서 자연스럽게 재현되지 않게 됨 — 근본 원인이라기보다 앱 설정이 불완전한 상태에서 발생하는 부수 증상이었던 것으로 추정
- **참고**: 미해결 상태로 남겨둠(재현되면 다시 조사 필요)

### 문제 3 (근본 원인): Meta 개발자 콘솔 개편으로 앱이 "Instagram 로그인" 방식으로만 설정돼 있었음
- **원인**: Meta가 앱 대시보드를 "제품 추가" 방식에서 **"이용 사례"(Use Cases)** 기반으로 개편함. 우리 앱은 **"Instagram 로그인이 포함된 API"**(`graph.instagram.com`, Facebook 페이지 불필요) 이용 사례로만 설정돼 있었는데, 이 화면에 "해시태그와 인사이트를 추적하려면 API setup with Facebook login으로 전환하세요"라는 안내가 있었음 — 즉 인사이트 추적은 **별도의 "Facebook 로그인이 포함된 API" 이용 사례**를 따로 설정해야 하는 기능이었음. 그 이용 사례의 "권한 및 기능" 목록을 열어보니 `instagram_manage_insights` 권한만 유일하게 "추가" 안 된 상태였음
- **해결**: 해당 권한을 앱에 추가(Standard Access라 앱 심사 없이 즉시 "테스트 준비 완료" 상태로 전환됨) → Graph API Explorer에서 새 토큰 재발급 → 동일 쿼리 재시도 → 정상 응답 확인
- **디버깅 방법이 유효했던 이유**: 공식 문서·웹서치로 현재 UI 구조를 파악하는 데 실패해서, `claude-in-chrome` 브라우저 자동화 도구로 사용자의 실제 로그인된 브라우저에 직접 접속해 대시보드를 눈으로 확인하는 방식으로 전환 — 이게 결정적이었음
- **참고**: `apps/insights-collector/README.md`

### 문제 4: `collect` 첫 dry-run에서 토큰 만료 (OAuthException code 190, subcode 463)
- **원인**: 오전에 받은 단기 토큰(1~2시간)을 장기 토큰으로 교환하지 않은 채 두어서 만료됨
- **해결**: 만료된 단기 토큰은 `exchange-token`으로도 교환 불가 → Graph API Explorer에서 새 단기 토큰 발급 → 바로 `npm run exchange-token`으로 60일 장기 토큰 교환(만료까지 59일, ~2026-11-26) → 재실행 성공
- **참고**: 만료 알림/자동 재교환은 아직 미구현 — 다음 작업으로 이월

### 문제 5: 계획서 Phase 3의 사진 수집 경로가 전부 사용 불가
- **원인**:
  - 카카오맵 `place.map.kakao.com/robots.txt`: `User-agent: *` / `Disallow: /` / `Allow: /$` — 루트 외 전 경로 수집 차단 (AI 봇은 별도로 명시 차단)
  - Google Places 정책: "You must not pre-fetch, cache, or store Places API content"(예외는 `place_id`뿐), photo name도 캐시 불가·만료. 카드 PNG에 합성해 인스타에 올리는 건 영구 저장·재배포라 출처 표기로도 해결 안 됨
  - 근본적으로 지도 앱의 "공식 사진"도 가게가 **그 플랫폼 안에서** 보여주라고 올린 것이라 제3자 재게시 권리가 없음. 블로그 OG 이미지도 같은 이유
- **해결**: 사진 확보를 사람(허락 요청/직접 촬영)으로 돌리고 연결만 자동화하는 구조로 전환 (완료한 작업 10~12)
- **참고**: 처음엔 Google Places를 "라이선스 부담이 적다"며 1순위로 추천했다가 정책 원문 확인 후 정정함. 네이버 지도 `robots.txt`는 도구 제약으로 직접 확인하지 못함

### 문제 6: Gemini 503으로 폴백 발생 — 성공 경로 재확인 또 실패
- **원인**: 09-27의 429(무료 할당량 소진)와 달리 503은 Google 서버 쪽 과부하. 계정 상태와 무관하게 그 시점 `gemini-3.8-flash` 용량 문제
- **해결**: 폴백은 설계대로 동작(재시도 3회 → Haiku). 다른 시간대에 재시도하기로 하고, 다음엔 사유를 볼 수 있게 에러 원문 로그 추가
- **참고**: Gemini 성공 경로 재확인은 계속 이월

### 문제 7: PowerShell 5.1에서 `git commit -m`에 큰따옴표가 든 메시지를 넘기면 인자가 쪼개짐
- **원인**: PowerShell 5.1이 네이티브 실행 파일에 인자를 넘길 때 내부 큰따옴표를 제대로 이스케이프하지 않아 `error: pathspec '사진만' did not match` 발생 (커밋은 안 됨, 스테이징만 된 상태)
- **해결**: 메시지를 파일로 쓰고 `git commit -F <파일>`로 커밋

### 문제 8: PowerShell `Set-Content -Encoding utf8`로 만든 `credit.txt` 앞에 BOM이 붙음
- **원인**: Windows PowerShell 5.1의 `utf8` 인코딩은 BOM 포함 UTF-8로 저장 → 출처 문자열 앞에 보이지 않는 `﻿`가 섞일 수 있음
- **해결**: `match.js`에서 읽을 때 선행 BOM 제거

## 💡 배운 점 / 메모

- Meta 같은 대형 플랫폼의 개발자 콘솔 UI는 예고 없이 개편될 수 있고, 개편 전 기준으로 안내하면(예: "제품 추가" 버튼) 실제 화면과 안 맞아서 오히려 혼란만 키운다 — 화면 구조 자체가 의심되면 문서를 더 뒤지기보다 실제 화면을 직접 보는 게 빠르다
- 공식 문서/웹서치로 명확한 답이 안 나올 때, 브라우저 자동화 도구로 사용자의 실제 로그인 세션에 직접 들어가서 화면을 보는 게 가장 확실하고 빠른 진단 방법이었다 — 특히 인증이 필요한 콘솔/대시보드 문제는 텍스트 기반 문서 검색보다 실제 화면 확인이 압도적으로 효율적
- 에러 메시지가 애매해도(`nonexisting field`, `Invalid platform app`) 실제 원인은 권한 하나가 빠진 것처럼 단순한 경우가 많다 — 에러 문자열 자체를 붙잡고 검색하기보다, 권한/설정 체크리스트를 하나씩 소거법으로 확인하는 게 결국 더 빠른 경로였음
- 외부 API의 "계획 당시 가정"은 시간이 지나면 깨질 수 있다 — 오늘도 `impressions`/`profile_views` 메트릭이 계획서 작성 이후 사라진 걸 확인했다. 이번에도(지난번 네이버 API HUB 이관처럼) 최신 공식 문서를 직접 확인하는 습관이 실제로 시간을 아껴줬다
- 일별 집계 배치는 "언제 실행되든 같은 날짜 구간을 본다"가 핵심 — API 기본 기간에 맡기지 말고 `since/until`을 명시해야 크론 지연(GitHub schedule은 수~수십 분 밀리기도 함)이나 재실행에도 결과가 안 흔들린다
- 과거 값을 조회할 수 없는 스냅샷 지표(`followers_count`)는 실행 시각이 곧 측정 시각 — 재수집(`--date`)으로 복구할 수 없으니 하루라도 빠지면 영구 결측이 된다
- 단기 토큰은 받자마자 장기 토큰으로 교환할 것. 만료된 단기 토큰은 교환 재료로도 못 쓴다
- `gh run watch`는 비대화형 셸에선 run ID를 필수로 요구함. 결과만 볼 거면 `gh run view <id>`로 충분
- GitHub Actions `schedule`은 UTC 기준이고, 공개 저장소는 60일간 커밋이 없으면 자동 비활성화됨
- 외부 콘텐츠를 쓰는 자동화는 **구현 전에 약관·`robots.txt`·정책 원문부터** 확인할 것. "공식 API니까 괜찮다"는 가정이 틀릴 수 있다 (Google Places: 호출은 합법이지만 결과 저장·재배포는 금지)
- "자동화할 수 없는 부분(허락 요청)은 사람에게 두고, 그 앞뒤(대상 찾기, 결과 반영)를 자동화한다"는 분할도 설계 결정이 된다 — 전부 자동화하려다 막히는 것보다 낫다
- 규칙은 문서보다 코드로 강제하는 게 확실하다 — 출처가 비어 있으면 사진을 쓰지 않도록 `match.js`에서 막음
- 독립 CLI 여러 개를 잇는 오케스트레이터는 import보다 자식 프로세스(cwd = 앱 폴더)가 단순하다. 각 앱의 `.env`/의존성 경계가 그대로 유지됨
- 개발 서버 미들웨어로 로컬 파일을 서빙할 땐 경로 조작(`../`) 차단을 반드시 넣고, 실제 요청으로 막히는지 확인할 것
- Windows PowerShell 5.1 주의점 두 가지: 네이티브 명령 인자 속 큰따옴표가 깨짐(→ 파일로 전달), `-Encoding utf8`은 BOM 포함
